# 범용 상품군과 구매 옵션 후보 설계

- 작성일: 2026-08-08
- 상태: planned
- 적용 범위: 상품 후보 묶음/판매처 상품/구매 옵션/후보 재정렬/사용자 선택 UI

## 1. 목적

현재 후보 검색은 판매처 상품 한 행을 카드 하나로 반환한다. ABC마트에서 같은 이름의
상품이 색상별 판매처 상품 번호로 나뉘면 같은 이름의 카드가 여러 번 나타나며, 후보를
3건으로 먼저 제한한 뒤 선호 조건을 설명하기 때문에 실제 상품 종류가 더 정확한 후보가
뒤로 밀릴 수 있다.

이 문제는 신발에만 한정되지 않는다. 의류는 색상/사이즈, 가방은 색상/용량, 가구는
색상/소재/규격, 전자제품은 색상/모델/저장 용량이 구매 선택을 나눈다. 따라서 최종 후보는
판매처 상품 행이 아니라 사용자가 하나의 상품으로 인식하는 상품군을 기준으로 보여주고,
카드 안에서 실제 구매 가능한 판매처 상품과 옵션을 선택할 수 있어야 한다.

## 2. 현재 관찰 결과

### 2.1 ABC마트 후보 중복

2026-08-08 로컬 PostgreSQL에서 `밸롭 구름 브리즈`는 같은 이름과 카테고리 아래 서로
다른 판매처 상품 번호로 저장돼 있었다.

| 판매처 상품 번호 | 대표 색상 |
|---|---|
| `7000026563` | `BLACK` |
| `7000026564` | `BLACK` |
| `7000026565` | `BEIGE` |
| `7000026566` | `ORANGE` |
| `7000026567` | `PURPLE` |
| `7000026568` | `WHITE` |

이 상품들은 `신발 > 스포츠 > 워킹화`지만 `구두` 수집 작업에서 발견됐다는 이유로
후보에 포함됐다. 현재 검색 문서는 상품명/브랜드 중심이고 카테고리의 상품 종류 근거가
약하며, 선호 조건 판정 전에 최대 3건으로 제한하므로 같은 워킹화가 반복되고 실제 로퍼가
뒤로 밀렸다.

같은 이름과 색상인 두 행도 실제로 같은 구매 옵션이라고 단정할 수 없다. 판매처의
상위 상품 ID나 모델 코드가 없으면 합치는 대신 하나의 상품군 안에 별도 판매처 상품으로
보존해야 한다.

### 2.2 여러 상품군 소량 수집

2026-08-08 29CM 공개 검색에서 가방/셔츠/의자/헤드폰을 각각 5건, 검색 요청 1회로
제한해 수집했다. 20건 모두 공통 Contract를 통과했지만 각 검색의 누락 필드 합계는
30이었고 `options.colors`와 `options.sizes`는 모두 비어 있었다.

| 상품군 | 상품명에 보인 구매 속성 예 | 현재 구조화 결과 |
|---|---|---|
| 가방 | `20L`, `50L 90L`, `2 colors` | 색상/용량 옵션 없음 |
| 셔츠 | `라이트핑크`, `Navy`, `MDSH019WHITE` | 색상/사이즈/품번 없음 |
| 의자 | `Black / Chrome`, `화이트 오크`, `10colors` | 색상/소재/규격 옵션 없음 |
| 헤드폰 | `4colors`, `WH-CH720N`, `WH-CH520` | 색상/모델 옵션 없음 |

상품명 문자열에서 보이는 값을 판매처 사실로 자동 확정해서는 안 된다. 검색 단계에서는
후보 회수 단서로만 사용할 수 있고, 실제 선택지는 공개 상세 응답에서 옵션 ID/재고/가격과
함께 수집해야 한다.

## 3. 설계 결론

후보를 다음 세 수준으로 구분한다.

```text
상품군 ProductGroup
  └── 판매처 상품 MerchantListing
        └── 구매 옵션 PurchasableOption
```

- `ProductGroup`: 사용자가 비교 카드 하나로 인식하는 상품군이다.
- `MerchantListing`: 판매처 상품 번호/URL/대표 이미지/현재 가격을 가진 실제 판매 행이다.
- `PurchasableOption`: 색상/사이즈/용량/소재 같은 속성 조합과 재고/추가 가격을 가진
  구매 선택지다.

PostgreSQL의 기존 `merchant + externalId` 식별 규칙은 유지한다. 상품군 묶음은 원본 행을
없애거나 덮어쓰지 않는 별도 읽기 모델이며, 묶음이 불확실하면 합치지 않는다.

## 4. 범용 속성 계약

`size`와 `color`는 자주 사용하는 편의 필드로 유지할 수 있지만 모든 상품군의 기준으로
사용하지 않는다. 판매처 상품과 구매 옵션은 범용 속성 map을 함께 제공한다.

```json
{
  "optionId": "merchant-option-123",
  "label": "화이트 오크 / W500",
  "attributes": {
    "color": "WHITE",
    "material": "WHITE_OAK",
    "width": {"value": 500, "unit": "mm"}
  },
  "stockStatus": "available",
  "price": {"amount": 129000, "currency": "KRW"},
  "provenance": {
    "sourceUrl": "https://example.com/product/123",
    "collectedAt": "2026-08-08T10:00:00+09:00",
    "collectorVersion": "example"
  }
}
```

속성 key는 공통 vocabulary를 우선 사용하고 판매처 전용 속성은 namespace를 붙인다.
값을 정규화할 수 없으면 원문 label을 보존하며 추측한 값을 만들지 않는다.

## 5. 상품군 묶음 규칙

묶음 근거의 우선순위는 다음과 같다.

1. 판매처가 제공한 상위 상품 ID나 variant group ID
2. 판매처 모델 코드/스타일 코드와 브랜드/카테고리 일치
3. 같은 판매처의 정규화한 브랜드/상품명/카테고리 일치
4. 판매처 간 묶음은 검토된 모델 식별자가 있을 때만 수행

각 상품군에는 `groupingBasis`, `groupingConfidence`와 사용한 필드를 기록한다. 3번처럼
파생 규칙을 사용하면 `DERIVED`로 표시한다. 이름만 같은 상품, 카테고리가 다른 상품,
모델 식별자가 충돌하는 상품은 묶지 않는다.

## 6. 후보 검색과 재정렬

후보 3건을 먼저 제한하지 않는다. 구조화 필터와 Hybrid Retrieval로 더 넓은 판매처
상품 pool을 회수한 뒤 다음 순서로 처리한다.

```text
필수 조건 filter
  ↓
상품 종류/상품명/브랜드/카테고리 관련성 계산
  ↓
선호 옵션 일치/최신성/근거 완전성 판정
  ↓
상품군 묶음과 대표 판매처 상품 선택
  ↓
상위 상품군 최대 5개 선택
  ↓
선택된 상품군의 전체 판매 행/컬러 확장 조회
```

수집 당시 검색어는 회수 근거 중 하나일 뿐 상품 종류 일치로 취급하지 않는다. `구두`
수집 작업에서 발견된 워킹화보다 상품명이나 카테고리가 구두/로퍼인 후보를 먼저 보여야
한다. 임의 합계 가중치는 고정하지 않고 검색 평가 data로 정하되, 응답에는 점수 구성과
완화 이유를 분리해 반환한다.

## 7. 후보 응답 초안

```json
{
  "groupId": "derived:abcmart:ballop:구름-브리즈:워킹화",
  "name": "밸롭 구름 브리즈",
  "brand": "밸롭",
  "categoryPath": ["신발", "스포츠", "워킹화"],
  "groupingBasis": "DERIVED",
  "groupingConfidence": 0.8,
  "selectedListingId": 101,
  "listings": [
    {
      "listingId": 101,
      "externalId": "7000026563",
      "attributes": {"color": "BLACK"},
      "availableOptions": [
        {"optionId": "270", "attributes": {"size": "270"}, "stockStatus": "available"}
      ],
      "price": {"amount": 49900, "currency": "KRW"},
      "productUrl": "https://example.com/7000026563"
    }
  ],
  "retrievalSignal": {
    "keywordScore": 0.33,
    "freshnessScore": 0.8,
    "evidenceCompletenessScore": 1.0
  },
  "matchReasons": ["270 재고 확인", "검정 판매처 상품 확인"],
  "relaxedConditions": ["용도 출근 평가 근거 없음"]
}
```

기존 후보 응답과 MCP/Web 호환성을 고려해 상품군 응답은 additive contract로 먼저
도입하고, 소비자가 전환된 뒤 판매처 상품 단위 후보 필드의 제거 여부를 결정한다.

조건 검색은 상품군의 순위를 정하는 단계와 사용자가 둘러볼 전체 판매 행을 조회하는
단계를 분리한다. 요청 사이즈나 색상을 만족하지 않는 판매 행도 상위 상품군에 속하면
응답에 포함하고 `MISMATCH`/`UNKNOWN`과 이유를 표시한다. 따라서 사용자는 다른 컬러를
볼 수 있지만 구매 가능한 선택지로 오해하지 않는다.

## 8. 사용자 화면 동작

- 같은 상품군은 카드 하나로 표시한다.
- 추천 상품군은 조건을 통과한 범위에서 최대 5개를 표시한다.
- 색상/용량/소재 같은 선택지를 상품군의 실제 `listings`와 `options`에서 만든다.
- 선택지를 바꾸면 이미지/가격/재고/사이즈/상품 URL도 같은 판매처 상품 기준으로 바뀐다.
- 조건에 맞지 않는 컬러도 숨기지 않고 품절/요청 사이즈 없음/확인 필요 상태로 구분한다.
- 같은 색상의 판매처 상품이 둘 이상이면 모델 코드나 판매처 상품 번호를 함께 보여
  사용자가 구분하게 한다.
- 옵션 정보가 없으면 선택 UI를 만들지 않고 `상세 옵션 확인 필요`로 표시한다.
- 최종 선택한 판매처 상품과 옵션을 구매 전 재검증 대상으로 전달한다.

## 9. 수집 확장 방안

검색 수집과 상세 수집을 분리한다.

1. 상품군별 검색어로 기본 상품/카테고리/가격을 넓게 수집한다.
2. 검색 응답의 모델 코드/상위 상품 ID/대표 속성을 가능한 범위에서 구조화한다.
3. 상위 후보만 상세 작업으로 보내 실제 옵션 ID/속성 조합/재고/가격을 수집한다.
4. 신발 외 fixture에는 최소 의류/가방/가구/전자제품을 포함한다.
5. 상품군별 속성 누락률/상품군 오병합률/카드 중복률을 품질 지표에 추가한다.

대량 수집은 상품군 구조를 알아내기 위한 선행 조건이 아니다. 먼저 상품군별 소량
fixture로 Contract와 parser를 검증하고 판매처별 요청 예산/최소 간격을 지킨 뒤 범위를
확대한다.

## 10. 완료 조건

- 같은 상품군의 여러 판매처 상품이 후보 카드 하나에 묶이고 원본 판매처 상품은 모두
  추적 가능하다.
- 묶음 근거와 confidence가 응답에 포함되며 불확실한 상품은 합치지 않는다.
- 필수 조건을 위반하지 않는 넓은 후보 pool을 상품 종류/선호 조건으로 재정렬한 뒤
  상위 상품군을 최대 5개 반환한다.
- 상위 상품군의 전체 판매 행을 조건과 무관하게 확장하고 행별 조건 상태를 반환한다.
- 색상이나 다른 속성을 바꾸면 해당 판매처 상품의 이미지/가격/재고/URL이 함께 바뀐다.
- 신발/의류/가방/가구/전자제품 fixture에서 범용 속성 계약을 자동 검증한다.
- 검색 단계에 옵션이 없으면 상세 수집 전까지 확인 필요로 표시하고 값을 추측하지 않는다.
- 상품군 오병합/중복 카드/옵션 출처 누락을 측정하는 회귀 테스트가 통과한다.
