# 기능 ID 기반 개발 추적 프로세스

작성일: 2026-07-31

## 목적

아키텍처에서 정의한 기능이 실제 코드, 테스트, 변경 기록과 진행상황 문서에서 서로
다른 이름으로 관리되는 문제를 막는다. 하나의 기능 ID로 계획부터 완료 판정까지
연결한다.

## 문서별 책임

| 문서 | 답하는 질문 | 변경 주체 |
|---|---|---|
| `docs/architecture/*.md` | 무엇을 왜 만드는가 | 기획과 설계 작업 |
| `docs/planning/Purchase_Research_Agent_기능_목록.md` | 어떤 기능이 있고 완료 기준은 무엇인가 | `feature-catalog` |
| `docs/planning/Purchase_Research_Agent_TODO.md` | 기능을 어떤 원자 작업으로 구현하는가 | 개발 작업 |
| `docs/reports/코드트래커/*` | 어떤 commit에서 무엇을 변경하고 검증했는가 | `code-tracker` |
| `docs/development/Purchase_Research_Agent_개발_진행_관리.md` | 실제 코드 기준으로 얼마나 완료됐는가 | `feature-progress` |
| `AGENTS.md` | 언제 어떤 스킬을 실행하는가 | 프로젝트 운영 규칙 |

## 스킬 책임

### `feature-catalog`

- 아키텍처에서 기능을 추출한다.
- 고정 기능 ID와 완료 기준을 관리한다.
- 기존 ID를 삭제하거나 재번호를 부여하지 않는다.
- 실제 구현 상태를 단독으로 완료 판정하지 않는다.

### `code-tracker`

- 하나의 기능 ID와 구현 commit을 연결한다.
- 변경 파일, 핵심 심볼, 문제 원인, 해결과 실제 검증을 기록한다.
- 기능 상태와 TODO 체크박스를 직접 변경하지 않는다.
- 구현 commit이 없는 완료 기록은 만들지 않는다.

### `feature-progress`

- 아키텍처, 기능 목록, TODO와 코드트래커를 읽는다.
- 실제 source, contract, migration, 설정과 test를 확인한다.
- 검증 명령을 실행하고 기능 상태를 판정한다.
- 기능 목록, TODO와 개발 진행 관리 문서를 함께 갱신한다.

## 개발 흐름

```text
아키텍처 작성 또는 변경
  ↓
feature-catalog
  ↓
기능 ID 선택 및 TODO 세분화
  ↓
코드 구현과 테스트
  ↓
구현 commit
  ↓
code-tracker
  ↓
feature-progress
  ↓
문서 commit
  ↓
push 및 PR
```

## 실행 시점

### 아키텍처를 변경했을 때

1. `$feature-catalog`를 실행한다.
2. 새 기능 ID 또는 변경된 완료 기준을 확인한다.
3. 구현할 기능의 TODO를 원자 작업으로 나눈다.

### 기능 구현을 시작할 때

1. 기능 ID가 존재하는지 확인한다.
2. 관련 TODO 항목에 `**(진행 중)**`을 표시한다.
3. 기능 ID 범위를 넘는 변경이 필요하면 기능 목록을 먼저 갱신한다.

### 구현과 테스트가 끝났을 때

1. 관련 검증 명령을 실행한다.
2. 코드와 필수 계약 또는 문서를 구현 commit에 포함한다.
3. `$code-tracker <기능-ID>`로 commit 기반 변경 기록을 작성한다.
4. `$feature-progress <기능-ID>`로 상태를 다시 판정한다.
5. 코드트래커와 상태 문서를 문서 commit으로 남긴다.

### PR을 만들기 전

1. `$feature-progress 전체 기능 상태를 점검해줘`를 실행한다.
2. 기능 목록, TODO와 개발 진행 관리의 상태 불일치를 해결한다.
3. 필수 검증과 `make docs-check`를 실행한다.

## 상태 변경 원칙

- 아키텍처와 기능 목록만 있으면 `계획`이다.
- 코드를 작성 중이지만 정상 경로가 없으면 `진행 중`이다.
- 정상 경로 일부만 동작하면 `부분 구현`이다.
- 코드는 갖춰졌지만 계약, 통합 또는 실제 검증이 남으면
  `구현 완료/검증 필요`다.
- 완료 기준 전체와 실패 경로, 테스트, 문서 및 검증이 확인돼야 `완료`다.
- 외부 결정 없이는 진행할 수 없으면 `차단`, 팀 결정으로 미루면 `보류`다.

## 기존 기록 처리

이 프로세스 도입 전의 TODO와 개발 기록은 삭제하거나 기능 ID를 억지로 소급해
변경하지 않는다. 새 작업과 현재 수정하는 기능부터 ID를 연결한다. 과거 기록을
참조해야 하면 코드트래커 또는 진행 관리에 관련 날짜와 기존 제목을 함께 남긴다.

## commit 처리

코드트래커는 구현 commit hash를 정확히 기록하기 위해 구현 commit 이후 실행한다.
코드트래커와 진행상황 문서는 별도의 문서 commit으로 남긴다. commit, push와 PR은
기존 Git 승인 절차를 그대로 따른다.
