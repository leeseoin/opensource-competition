## 배경과 범위

Python ABC마트/29CM 크롤러는 상품별 JSON/HTML 검증 결과를 만들고 Spring Boot를
통해 PostgreSQL에 저장했지만, API 최상위 집계는 `{"MATCHED": 3}` 형태였다. Go
Collector의 `verificationSummary`와 필드 이름 및 batch 의미를 맞추고, Python 결과가
공통 CollectorResult JSON Schema를 위반하면 Product Backend 전송 전에 차단하도록
정렬했다.

## 구현 내용

- `purchase-research-agent/app/services/verification_summary.py:17`
  `summarize_verifications`: 검증 결과가 있는 상품을 `total`, `matched`,
  `mismatched`, `failed`, `missingInHtml`, `missingInJson`, `pending`으로 집계한다.
- `purchase-research-agent/app/services/collector_result_validation.py:18`
  `validate_collector_result`: 공통 JSON Schema 위반 경로와 원인을 모아 전송 전에
  `ValueError`로 차단한다.
- `purchase-research-agent/app/services/collector_result_adapter.py:31`
  `build_collector_result`: 각 50개 저장 batch에 해당 batch의 검증 집계를 넣고 최종
  결과의 공통 계약을 검사한다.
- `purchase-research-agent/app/api/endpoints/store.py:38`
  `collect_and_store`: Swagger 응답에서도 Go와 같은 검증 집계 구조를 반환한다.
- `contracts/collector/v1/collector-result.schema.json:58`
  `verificationSummary`: Python과 Go가 함께 사용하는 집계 필드 계약을 정의한다.
- `services/product-backend/src/main/java/com/purchasesearch/product_backend/collection/dto/CollectorResult.java:40`
  `CollectorResult` 및 `VerificationSummary`: Spring Boot가 동일 집계를 역직렬화하고
  음수 개수를 거절한다.

## 발생 문제와 원인

- Python API의 동적 상태 map과 Go의 고정 필드 집계가 달라 같은 의미의 결과를
  화면과 Backend에서 공통으로 읽을 수 없었다.
- 검증 결과가 없는 상품에도 `verification: null`을 넣으면 JSON Schema의 객체
  조건을 위반했다.
- Python Adapter는 원본 상품 Contract만 검사하고 최종 CollectorResult는 런타임에
  검사하지 않았다.

## 해결

- 상태를 고정된 공통 필드에 매핑하고 검증 결과가 있는 상품만 `total`에 포함해 Go의
  집계 규칙과 맞췄다.
- 검증 결과가 없으면 `verification`과 `verificationSummary` 자체를 생략했다.
- batch 생성 직후 공통 JSON Schema를 검사해 잘못된 상태와 필드 구조가 DB 요청까지
  넘어가지 않도록 했다.
- 수집 원본은 `output/raw_json/{merchant}`와 `output/raw_html/{merchant}`에 계속
  분리 저장하고, 모든 `output/` 디렉토리는 Git 추적에서 제외했다.
