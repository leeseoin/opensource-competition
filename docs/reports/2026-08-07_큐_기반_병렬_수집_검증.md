# 큐 기반 병렬 수집 검증 — asyncio.Semaphore의 프로세스 경계 문제 해결

작성일: 2026-08-07
대상: `purchase-research-agent` — 10,000개 규모 수집을 위해 OS 프로세스를 여러 개 띄워
병렬 처리하려던 시도에서 발견된 문제와, 이를 큐 기반 워커 풀로 해결한 과정.

## 문제: 프로세스를 여러 개 띄우면 세마포어가 무력화된다

`run_unified_crawl.py`는 프로세스 1개 안에서 `asyncio.Semaphore`(`keyword_concurrency`)로
동시 처리 조합 수를 제한한다. 이 방식은 프로세스 1개, `keyword_concurrency=3`, 8개
조합(2,000개 목표) 기준 **99.9% 성공**(1,999/2,000, 2026-08-06 리포트 참고)을 냈다.

10,000개를 노리며 이 스크립트를 별도 OS 프로세스 2개로 20초 간격 병렬 실행해봤더니
목표 대비 35~39%밖에 못 채우고 ANTIBOT/타임아웃이 급증했다. 원인은 `asyncio.Semaphore`가
**프로세스 로컬**이라는 점 — 프로세스 2개는 서로의 존재를 모른 채 각자 세마포어 한도까지
동시 요청을 쏘고, 둘 다 같은 로컬 머신의 CPU/네트워크 연결을 공유하므로 실제 동시
부하는 두 세마포어 한도의 합만큼 치솟는다.

## 1차 조치: ABC마트 detail_fetcher 동시성 캡 추가

`abcmart/detail_fetcher.py`는 상세 페이지(`crawl4ai.arun_many`, 세마포어 없음, crawl4ai
기본값 20)와 리뷰/옵션 API(`asyncio.gather`, 무제한)를 캡 없이 쐈다. 29CM 쪽
(`cm29/detail_fetcher.py`, `cm29/verification.py`)은 이미 `asyncio.Semaphore(10)`으로
캡이 걸려 있었다. ABC마트에도 같은 캡(`browser_concurrency=5`, `api_concurrency=10`)을
추가했더니 프로세스 2개 병렬 실행 합계가 1,482개 → 1,932개로 개선됐지만(+30%), 한
배치의 29CM(코드를 건드리지 않은 부분)이 오히려 나빠지는 현상이 나타났다 — **프로세스
간 자원 경쟁은 프로세스 내부 캡만으로는 못 없앤다**는 걸 재확인.

## 2차 조치: 큐 기반 워커 풀로 아키텍처 교체

`asyncio.Semaphore`는 프로세스를 못 넘어가는 도구이므로, 애초에 "프로세스별 세마포어"가
아니라 "여러 프로세스가 공유하는 큐"로 동시성을 통제하는 구조로 바꿨다
(`scripts/run_queue_crawl.py`). (키워드, 사이트) 조합을 하나의 공유 큐에 넣고, 고정된
수의 워커 프로세스가 큐에서 한 번에 하나씩만 꺼내 처리한다 — 워커가 몇 개든 시스템
전체 동시 처리량은 정확히 "워커 수"로 고정되고, 이 한도를 큐 하나가 전역으로 관리한다.

RabbitMQ가 이 리포지토리의 `compose.yaml`에 이미 정의돼 있지만, 이 환경에는 Docker가
없어 브로커를 띄울 수 없었다. 그래서 파이썬 표준 라이브러리인 `multiprocessing.Queue`로
같은 구조(공유 큐 + 고정 워커 수)를 먼저 검증했다. 워커 본체(크롤링 로직)와 큐 인터페이스
(`queue.get()` / `put(None)` 센티널)를 최소화해뒀기 때문에, 나중에 Docker로 RabbitMQ를
띄우면 큐 트랜스포트만 aio-pika로 교체하고 워커 로직은 그대로 재사용할 수 있다.

## 검증 과정과 실측 결과

| 시도 | 구성 | 결과 | 비고 |
|---|---|---|---|
| 프로세스 2개, 세마포어(수정 전) | 20초 간격, 각자 `keyword_concurrency=2` | 1,482/4,000 (37%) | ANTIBOT/타임아웃 다수 |
| 프로세스 2개, 세마포어(ABC마트 캡 추가 후) | 위와 동일 | 1,932/4,000 (48%) | 29CM 쪽이 되레 악화 — 프로세스 간 경쟁 확인 |
| 큐, 워커 4개, 동시 기동 | 16개 조합(8키워드×2사이트), 250개씩 | 1,899/4,000 (47%) | 워커 4개가 동시에 첫 요청을 쏘며 DNS 조회 폭주(`getaddrinfo failed`) 발생 — 새로운 실패 유형 발견 |
| 큐, 워커 4개, 기동 1.5초 지터 | 동일 | 3,304/4,000 (83%) | DNS 폭주는 해소. 남은 미달은 키워드 자체 재고 한계(어그: 63/66개)와 검색 페이지네이션 중 예외 1건(부츠/abcmart 30개) |
| 큐, 워커 4개, 기동 지터 + 페이지 재시도 1회 | 14개 조합(재고 한계 키워드 "어그" 제외), 250개씩 | **3,395/3,500 (97.0%)** | 목표 미달은 "워커" 키워드의 실제 재고 한계(145개)뿐, 그 외 13개 조합 전부 목표치 100% 달성 |

## 추가로 고친 버그 2건

- **ABC마트 검색 페이지네이션에 재시도가 없었다**: 페이지 요청 중 예외가 한 번이라도
  나면 남은 페이지 전체를 포기하고 즉시 중단했다. 실측에서 이 때문에 목표 250개 중
  30개만 수집되고 220개를 날린 사례를 확인(`부츠/abcmart`). 실패 시 짧은 대기 후 1회
  재시도하도록 고쳤다(`app/crawlers/abcmart/crawler.py`).
- **워커 동시 기동 시 DNS 조회 폭주**: 워커 프로세스 여러 개가 정확히 같은 순간에 첫
  요청을 보내면 로컬 DNS 조회가 몰려 `getaddrinfo failed`로 즉시 실패하는 조합이
  생겼다. 워커 기동 사이에 1.5초 지터를 둬서 해소했다(`scripts/run_queue_crawl.py`).

## 결론

- 원인은 "동시성이 높아서"가 아니라 **"asyncio.Semaphore가 프로세스 경계를 못 넘는다"**
  는 도구 선택 문제였다. 같은 동시성 수준(워커/프로세스 4개)이라도 조율 방식이 프로세스
  로컬 세마포어냐 공유 큐냐에 따라 성공률이 48% → 97%로 갈렸다.
- 남은 미달분은 크롤러의 실패가 아니라 **키워드 자체의 실제 검색 결과 수 한계**다(예:
  "어그" 29CM 63개, "워커" abcmart 145개 — 두 번의 독립된 실행에서 정확히 같은 수치가
  나와 이를 뒷받침한다).
- 지금은 `multiprocessing.Queue`로 검증했지만, 여러 머신으로 분산하거나 기존 RabbitMQ
  인프라와 통합하려면 Docker로 브로커를 띄우고 큐 트랜스포트를 aio-pika로 교체하면
  된다 — 워커 크롤링 로직은 변경할 필요가 없도록 설계해뒀다.
