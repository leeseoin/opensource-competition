# 2026년 오픈소스 개발자대회 결과보고서 — 담당 파트 작성 초안

> 이 문서는 `docs/inputs`의 결과보고서 서식·SBOM 가이드에 맞춰, 제가 직접 작업한
> `purchase-research-agent`(상품 정보 수집 서버)와 `contracts`(서비스 간 데이터 형식 약속) 두
> 폴더의 내용만 정리한 초안입니다. 프로젝트명·팀 정보·등록 URL·시연 영상처럼 팀 전체
> 기준으로 정해지는 항목은 `[ ]`로 표시했으니 최종 제출 전에 팀 논의 결과로 채워 넣으면
> 됩니다. 다른 팀원이 작업한 화면(프론트엔드)이나 다른 언어의 수집기(Go) 부분은 포함하지
> 않았습니다.

## 개발 배경 및 목적

여러 쇼핑몰의 가격과 재고를 비교해 주는 서비스를 만들려면, 그 전에 "정확한 상품 정보를
어떻게 모을 것인가"부터 풀어야 합니다. 사람이 직접 쇼핑몰 여러 곳을 돌아다니며 가격, 사이즈,
재고를 확인하는 일은 시간이 오래 걸리고, 데이터를 한 번 모으고 끝나는 게 아니라 가격이
바뀔 때마다 다시 확인해야 합니다.

제가 맡은 부분은 이 문제를 해결하는 수집 서버입니다. 목표는 두 가지였습니다.

1. 쇼핑몰 화면을 자동으로 방문해 상품명·가격·리뷰·옵션(사이즈/색상)을 정기적으로 가져오는
   프로그램을 만드는 것
2. 가져온 정보가 실제 화면과 다르지 않은지 스스로 한 번 더 확인해서, "출처를 알 수 없는
   값"이나 "잘못 읽은 값"이 그대로 저장되지 않게 하는 것

또한 이 수집 서버는 혼자 동작하는 프로그램이 아니라, 다른 팀원이 만드는 백엔드 서버(자바)와
데이터를 주고받아야 했습니다. 그래서 "누가 어떤 모양의 데이터를 주고받을지"를 문서와 JSON
형식으로 미리 정해 두는 작업(`contracts` 폴더)도 함께 진행했습니다. 서로 다른 언어로 개발하는
팀원들이 매번 말로 확인하지 않아도 되도록 하기 위해서입니다.

## 개발 환경

- 언어/런타임: Python 3.12
- 웹 서버 프레임워크: FastAPI + uvicorn
- 쇼핑몰 화면 자동 조작: Crawl4AI(Playwright 기반 브라우저 자동화), BeautifulSoup4(HTML 분석)
- 상세 정보 API 호출: httpx
- 다른 서버와의 작업 주고받기: RabbitMQ(메시지 큐) + aio-pika
- 데이터 형식 검증: Pydantic, jsonschema
- 패키지·버전 고정: uv (`pyproject.toml`, `uv.lock`)
- 실행/검증 자동화: 저장소 루트의 `make python-crawler-setup`, `make python-crawler-run`,
  `make python-crawler-worker` 등 명령
- 테스트: pytest (`tests/` 폴더, 크롤러·검증·큐·안전장치 단위로 분리)

## 시스템 구성 및 아키텍처

담당 파트는 크게 세 덩어리로 나뉩니다.

```
[쇼핑몰 화면 자동 방문]
  AbcMartCrawler / Cm29Crawler   → 목록 페이지에서 상품 기본 정보 수집
  DetailFetcher                  → 상위 상품만 리뷰·옵션 추가 수집(요청 간 지연 적용)
  Verification                   → 검색 결과(JSON)와 실제 화면(HTML)을 서로 대조

        ↓ 수집 결과를 계약(JSON Schema)에 맞는 모양으로 변환

[다른 서버와 데이터 주고받기]
  Backend(자바) → RabbitMQ 작업 큐 발행
                    ↓
  Python 수집 서버(Worker)가 작업을 하나씩 꺼내 처리
                    ↓ 쇼핑몰 수집 + 검증
  Python 수집 서버 → RabbitMQ 결과 큐로 응답 발행
                    ↓
  Backend(자바)가 형식을 검사한 뒤 데이터베이스에 저장

[데이터 형식 약속: contracts 폴더]
  collection/v1   : 큐로 주고받는 작업/결과 메시지의 형식
  collector/v1    : 검색 요청과 수집 결과의 형식(가격은 숫자+통화 코드, 출처 URL·수집 시각 포함)
  collector/v1-abcmart : ABC마트 실제 수집 코드가 만들어내는 값과, 백엔드가 실제로 저장하는
                          형식을 하나하나 대조해 어긋나는 지점을 찾아 정리한 문서
  collector/unified    : 파이썬 수집기와 (개발 예정인) Go 수집기의 결과를 같은 모양으로 맞춰
                          두 결과를 비교하기 위한 별도 형식
```

수집 서버는 요청을 받으면 즉시 응답하는 방식이 아니라, 작업을 큐에서 받아 처리하고 결과를
다시 큐로 돌려주는 방식으로 동작합니다. 한 번에 처리할 작업이 많아지거나 쇼핑몰 쪽 응답이
느려져도 전체 서비스가 멈추지 않도록 하기 위한 구조입니다.

## 프로젝트 상세 내용

### 핵심 기능 및 특징

- **카테고리·검색어 기반 자동 수집**: 신발, 의류 등 카테고리 페이지를 순서대로 넘기며 상품
  목록을 모으고, 그중 상위 상품에 한해 리뷰와 사이즈·색상 옵션까지 추가로 가져옵니다.
- **결과 자체 검증**: 검색 API가 돌려준 값과 실제 상세 화면에 있는 값을 서로 비교해서, 값이
  다르면 "다르다"는 사실 자체를 기록으로 남깁니다. 잘못된 값을 조용히 정답인 것처럼 저장하지
  않기 위한 장치입니다.
- **실패를 숨기지 않는 상태 값**: 수집이 절반만 성공했거나, 로그인·차단으로 막혔거나, 아직
  지원하지 않는 페이지 형식을 만났을 때 이를 각각 다른 상태 값(`success` / `partial` /
  `blocked` / `unsupported` / `temporarily_unavailable`)으로 구분해 응답합니다. 성공/실패
  두 가지로만 뭉뚱그리지 않는 것이 핵심입니다.
- **일시적인 오류는 재시도, 영구적인 오류는 재시도하지 않음**: 잠깐 응답이 느린 경우(429,
  5xx)만 재시도 큐로 보내고, 로그인 필요나 접근 차단(401/403)처럼 다시 시도해도 똑같이
  실패할 상황은 곧바로 실패로 종료해 불필요한 재시도를 하지 않습니다.
- **안전한 수집 원칙 준수**: 쇼핑몰의 `robots.txt` 허용 범위를 지키고, 인증서 검증을
  건너뛰지 않으며, 자동 리다이렉트를 무조건 따라가지 않습니다. 이런 값들이 실수로 다시
  느슨해지지 않도록 정적 검사 스크립트(`make python-crawler-safety-check`)를 따로 두었습니다.
- **개인정보 최소 수집**: 리뷰 작성자의 이름, 프로필 주소, 계정 식별값은 아예 가져오지
  않고, 리뷰 이미지도 파일을 내려받지 않은 채 "이미지가 있다/없다" 여부만 남깁니다.
- **서비스 간 데이터 형식 약속(계약)**: `contracts` 폴더에 JSON Schema로 형식을 정해두고,
  실제 코드가 그 형식을 지키는지 검사합니다. 이번에 ABC마트 실제 수집 값과 백엔드 저장 값을
  하나씩 맞춰보다가, 리뷰 식별값이 비어 있을 수 있는 문제, 가격이 문자열로 넘어가 숫자 변환에
  실패하면 통째로 비어버리는 문제처럼 실제로 어긋나는 지점 다섯 가지를 찾아 문서로 남겼습니다
  (`contracts/collector/v1-abcmart/README.md`).

### 개발 과정(주요 단계)

1. 먼저 한 쇼핑몰(ABC마트)의 목록 페이지를 방문해 상품명·가격을 가져오는 가장 단순한 형태로
   시작했습니다.
2. 가져온 값이 실제 화면과 다를 수 있다는 문제를 발견한 뒤, 검색 결과와 상세 화면을 서로
   대조하는 검증 단계를 추가했습니다.
3. 상품을 대량으로 수집할 때 요청 하나하나를 즉시 처리하는 방식으로는 안정적으로 처리하기
   어려워, 작업을 큐에 쌓아두고 순서대로 처리하는 방식(RabbitMQ)으로 구조를 바꿨습니다.
4. 다른 언어(자바)로 만들어지는 백엔드 서버와 함께 개발이 진행되면서 "내가 보낸 값과 상대가
   기대하는 값이 다른" 문제가 여러 번 생겼습니다. 이를 막기 위해 주고받는 데이터의 형식을
   JSON Schema 문서로 먼저 정하고, 실제 코드가 그 형식을 지키는지 검사하는 절차를
   추가했습니다.
5. 두 번째 쇼핑몰(29CM)을 추가하면서, 검색 화면만으로는 상품 카드 정보가 부족해 상품별
   상세 화면까지 하나씩 확인하는 방식을 추가로 구현했습니다.

## 구동 및 시연

1. 저장소 루트에서 `make python-crawler-setup`(최초 1회), 이후 `make python-crawler-run`으로
   수집 서버를 띄웁니다.
2. 큐 등록부터 데이터베이스 저장까지 전체 흐름을 한 번에 확인하려면 `make
   python-crawler-swagger` 명령 하나로 관련 서버를 모두 함께 실행합니다.
3. 브라우저에서 `http://localhost:8012/docs`(FastAPI 자동 생성 문서)를 열고 번호 순서대로
   실행합니다.
   - `00 준비 확인` → 연결 상태 확인
   - `01 작업 등록` → 소량 수집 작업 등록, 작업 번호 확인
   - `02 진행 조회` → 작업 번호로 진행 상태와 수집 개수 확인
   - `03 결과 조회` → 실제로 저장된 상품·가격·옵션·출처 확인
4. 수집 결과는 `output/` 폴더에 JSON 파일로, 분석 리포트는 `logs/reports/`에 Markdown
   파일로 자동 저장됩니다. (`[여기에 실행 화면 스크린샷 또는 시연 영상 캡처 삽입]`)

## 기대효과 및 활용 분야

지금은 ABC마트·29CM 두 곳만 지원하지만, 쇼핑몰마다 다른 부분(목록 페이지 구조, 상세 API)만
따로 구현하면 새 쇼핑몰을 추가할 수 있는 구조로 만들어져 있습니다. 옷·신발 카테고리 외에
다른 상품군으로도 같은 방식으로 넓힐 수 있습니다. 또한 서비스 간 데이터 형식을 문서로 정해
두는 방식은 이번 프로젝트뿐 아니라, 여러 사람이 서로 다른 언어로 나눠 개발하는 다른
프로젝트에도 그대로 적용할 수 있는 방법입니다.

## 기타

### 프로젝트의 혁신성 및 차별성

- 자바로 만든 백엔드, 파이썬으로 만든 수집기, 앞으로 추가될 Go 수집기까지 서로 다른
  언어로 개발하면서도, 데이터 형식을 JSON Schema로 미리 정해 두어 안전하게 연결한 점.
- 수집한 값을 그대로 믿지 않고, 검색 결과와 실제 화면을 대조해 다른 값이 있으면 그 사실
  자체를 기록으로 남기는 검증 절차를 넣은 점.

### 한계점 및 향후 발전 로드맵

- 현재는 지원 쇼핑몰이 두 곳뿐이라 더 많은 쇼핑몰로 넓히는 작업이 남아 있습니다.
- 같은 작업이 실수로 중복 등록되는 것을 막는 기능(Redis 기반 중복 차단)은 아직
  설계만 되어 있고 실제로 켜져 있지 않습니다.
- 데이터 형식(JSON Schema)을 실행 중에 자동으로 검사하는 절차와, 이를 계속 확인하는
  자동화(CI)는 아직 갖춰지지 않아 다음 단계로 남겨 두었습니다.

### 소감 및 후기

`[직접 겪은 어려움과 해결 과정, 협업하며 느낀 점을 1인칭으로 자유롭게 작성]`

예시로 참고할 수 있는 흐름: 처음에는 "일단 값만 가져오면 되겠지"라고 생각했는데, 실제
화면과 대조해보니 값이 틀리는 경우가 있다는 걸 알고 검증 절차를 추가하게 된 과정, 다른
팀원의 백엔드와 데이터 형식이 맞지 않아 겪었던 시행착오, 그것을 계약 문서로 정리하면서
얻은 것 등을 구체적인 사례 중심으로 적으면 좋습니다.

## 붙임2. AI 모델 활용 및 라이선스 기술 명세서 — 참고

담당 파트(`purchase-research-agent`, `contracts`)는 실행 중에 AI 모델을 불러와 답변이나
예측을 만들어내는 코드가 없습니다. Crawl4AI는 이름에 "AI"가 들어가지만 실제로는 브라우저
자동 조작 라이브러리이며, 이 프로젝트에서는 모델을 불러오지 않고 페이지 접속·HTML 수집
용도로만 사용했습니다. 따라서 붙임2의 "활용 유형(유형1·2·3)" 체크 대상은 아닌 것으로
판단됩니다. 다만 개발 과정에서 코드 작성·디버깅 보조로 상용 AI 도구를 사용했다면 그 범위는
붙임2의 4번 항목(`상용 AI 보조도구 활용 여부 및 범위`)에 `[사용한 도구명과 대략적인 활용
비율]`로 기재하면 됩니다. 팀 전체에 AI 모델을 탑재·구동하는 다른 부분이 있는지는 다른
팀원의 작업 범위까지 함께 확인한 뒤 최종 판단하시기 바랍니다.
