# 1,999개 실수집 성능 분석 (병렬화 적용 후)

작성일: 2026-08-06
대상: `purchase-research-agent` — 오늘(2026-08-05~06) 적용한 29CM 검증/상세 병렬화,
페이지 간 jitter, 멀티 키워드 동시 실행, ABC마트 브랜드 크롤링 변경 이후 실측.

## 실행 파라미터

```bash
python scripts/run_unified_crawl.py "구두,스니커즈,운동화,부츠" 250 30 3
```

- 키워드 4개 × 사이트 2개(ABC마트/29CM) = 8개 (키워드, 사이트) 조합
- 조합당 `max_items=250` → 목표 총 2,000개
- `detail_limit=30` → 조합당 상위 30개 상품에만 리뷰/옵션 부착 (전체 2,000개 중 240개)
- `keyword_concurrency=3` → 8개 조합 중 최대 3개를 동시 진행

`detail_limit`을 전체(-1)가 아니라 30으로 제한한 이유: 사전 소규모 테스트에서 리뷰
1,500개가 넘는 상품이 여럿 나와, 전체 상세 수집을 시도하면 실행 시간이 과도하게
길어지고 장시간 지속 요청이 차단 위험을 높이기 때문. 검색·중복제거·검증(오늘
병렬화한 구간)은 목표 물량 그대로 부하 테스트하고, 리뷰/옵션 수집만 표본으로
제한하는 절충.

## 결과 요약

| 항목 | 값 |
|---|---|
| 총 실행 시간 | 4분 40초 (00:30:32 ~ 00:35:12) |
| 목표 수집 수 | 2,000개 (250 × 8 조합) |
| 실제 수집 수 | 1,999개 (abcmart 1,000 / 29cm 999) |
| Contract 위반 제외 | 1건 |
| 검증(JSON/HTML) 불일치 경고 | 11건, 전부 `image_url` 필드만 |
| 예외/페이지 로드 실패 | 0건 |
| 상세(리뷰/옵션) 부착 시도 | 240개 (조합당 30개) |
| 리뷰 데이터가 있는 상품 | 186개 |
| 수집된 리뷰 총량 | 48,721개 |
| 출력 파일 크기 | 37.1MB (`output/unified_구두외3건_1999_*.json`) |

목표 2,000개 중 1개만 빠졌고 그 1개는 버그가 아니라 **Contract가 정상적으로 걸러낸
사례**다 — 29CM 상품 하나가 색상×사이즈 옵션 문자열을 그대로 이어붙여 스키마의
VARCHAR 길이 상한을 넘겨 자동 제외됐다. 데이터 품질 관문이 의도대로 동작한 것으로 본다.

## 병렬화 효과 측정

ABC마트 쪽은 crawl4ai가 요청마다 소요 시간을 로그로 남겨 직접 비교할 수 있었다.

| 항목 | 값 |
|---|---|
| ABC마트 browser 요청 수 | 156건 |
| 요청별 소요 시간 합(=순차 실행 시 예상 시간) | 1,151초 (19분 12초) |
| 실제 전체 실행 시간(모든 사이트/조합 포함) | 280초 (4분 40초) |
| 체감 배율 | 약 **4.1배** |

ABC마트 요청 156건만 순차로 처리해도 19분이 넘게 걸릴 일이, 키워드 동시 실행
(`keyword_concurrency=3`)과 상세 수집 병렬화(`asyncio.gather`+`Semaphore`) 덕분에
29CM 처리까지 포함해서 4분 40초에 끝났다. 오늘 바꾼 구조(29CM 검증 병렬화, 상품
내부 상세+리뷰 동시 호출, 멀티 키워드 asyncio.gather)가 실측으로도 효과가
확인됐다.

로그에서도 병렬 동작이 직접 보인다 — 서로 다른 키워드의 `[ABCMART:full]`/
`[29CM:search]` 진행 로그와, 한 상품의 `[DETAIL]`/`[CM29:detail]` 로그가 순서대로
나오지 않고 뒤섞여 찍힌다(동시에 여러 조합·여러 상품이 진행 중이라는 뜻).

## 참고: ABC마트 키워드 검색 상한 재확인

이전 대화에서 `README.md`의 "키워드 기반 검색은 최대 64건 제한" 기록을 근거로
ABC마트 키워드 검색은 대량 수집에 부적합하다고 판단했었다. 그런데 이번 실행에서
"구두"/"스니커즈"/"운동화"/"부츠" 4개 키워드 모두 `max_items=250`을 그대로 채웠다
(조합당 250개, 250개, 250개, 250개 전부 정상 도달). 즉 이 64건 제한은 모든 키워드에
적용되는 게 아니라 **검색 결과가 원래 적은 특정 키워드에서만 나타나는 현상**이었을
가능성이 높다. `README.md`의 해당 설명은 실측과 다를 수 있어 업데이트가 필요해
보인다 — 다만 이번 확인은 4개 키워드에 한정되므로 단정하기보다는 "일반적인 키워드는
64건 제한을 안 받는다" 정도로만 반영하는 게 안전하다.

## 데이터 품질 메모

- `image_url` 불일치 11건은 전부 검색 결과 썸네일과 상세 페이지 이미지의 CDN
  파라미터(사이즈 변형 등) 차이로 보이며, 상품명/가격/브랜드 등 핵심 필드는 전부
  일치했다. 실제 데이터 오류라기보다 정규화 규칙을 더 다듬을 여지로 본다.
- Contract 위반 1건(옵션 문자열 길이 초과)은 스키마 검증이 실제로 오염 데이터를
  걸러낸 사례라 그대로 유지하는 게 맞다.

## 오늘 변경 사항과의 연결

이번 실행은 다음 변경 사항을 실제 트래픽으로 검증한 결과다.

- `app/crawlers/cm29/verification.py` — 검증 단계 `Semaphore` 병렬화
- `app/crawlers/cm29/detail_fetcher.py` — 상품 간 병렬화 + 상품 내부 상세/리뷰 동시 호출
- `app/crawlers/base.py` — `jittered_sleep()` 도입
- `scripts/run_unified_crawl.py` — 멀티 키워드 `asyncio.gather` + `return_exceptions=True`
- `app/crawlers/abcmart/crawler.py` — `BRANDS`/`crawl_by_brand()` 추가

8개 (키워드, 사이트) 조합, 상세 수집 240건, 리뷰 48,721개를 예외 없이 처리했고
치명적 에러 없이 4분 40초에 완료됐다.
