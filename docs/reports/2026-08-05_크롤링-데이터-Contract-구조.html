1. 한눈에 보기

두 판매처 크롤러는 각자의 원본 구조(v1-abcmart / v1-29cm)로 상품을 반환한다. contract_validation.py가 site별 스키마로 그 자리에서 걸러내고, 비교가 필요할 때만 normalizer.py가 하나의 통일 구조(v1-unified)로 평탄화한다.

검색 단계부터 갈라진다 — ABC마트는 검증에도 브라우저가 필요하고, 29CM은 끝까지 순수 HTTP로 끝난다. (2절·3절 참조)

2. ABC마트 vs 29CM — 수집 방식 비교

ABCMART
AbcMartCrawler
검색 데이터 원천검색 JSON (기본값)
검증 방법같은 검색 페이지 HTML 전수 대조
브라우저 필요필요 — 검색 화면이 JS 렌더링(SPA)
카테고리 크롤링지원 (17개 카테고리)
상세 수집 방식병렬 (arun_many + gather)
29CM
Cm29Crawler
검색 데이터 원천검색 JSON (유일한 원천)
검증 방법상품 상세 HTML의 JSON-LD 대조
브라우저 필요불필요 — 상세 HTML에 JSON-LD가 그대로 있음
카테고리 크롤링미구현 (키워드 검색만)
상세 수집 방식순차 (상품당 0.5초 딜레이)
왜 ABC마트만 브라우저가 필요한가 — ABC마트 검색/카테고리 페이지는 JS로 상품 카드를 렌더링하는 SPA라서 순수 HTTP GET으로는 상품이 안 보인다. 그래서 검증 단계에만 Crawl4AI(Playwright)를 쓴다. 29CM은 상세 페이지의 SEO용 Product JSON-LD가 렌더링 전 HTML에 그대로 박혀 있어서 검색·검증 전 구간을 httpx만으로 끝낼 수 있다.

같은 페이지·검색어의 검색 JSON과 렌더링 HTML을 상품ID 기준으로 연결해 title, brand, price, price_original, discount_percent, image_url, link 6개 필드를 대조한다.

status의미
MATCHEDJSON과 HTML 값이 모두 일치
MISMATCH하나 이상의 필드가 다름 — differences[]에 필드별 json_value/html_value 기록
MISSING_IN_HTMLJSON엔 있는데 렌더링 화면엔 없는 상품
FAILED해당 페이지 브라우저 로드 자체가 실패

5. Contract 구조

contracts/collector/

스키마는 세 계층으로 나뉜다. site별 원본 계약이 additionalProperties: false로 크롤러 출력을 그 자리에서 강제하고, 비교가 필요할 때만 normalizer.py를 거쳐 통일 계약으로 변환한다. 운영 저장 계약(Go Collector용)은 이 둘과 완전히 별개다.

계층위치강제 시점용도
v1-abcmart
v1-29cm		 contracts/collector/v1-{site}/ 크롤러가 상품 dict를 만드는 즉시 (contract_validation.validate_items) site별 원본 구조 보존 — 위반 상품은 그 자리에서 제외되고 errors에 기록
v1-unified contracts/collector/unified/ 비교가 필요할 때만, normalizer.normalize() 통과 후 ABC마트/29CM을 같은 필드로 비교·성능 측정 (Python/Go 등)
v1 (운영) contracts/collector/v1/ — 아직 미구현 (Go Collector + RabbitMQ 전제) provenance 포함 정식 저장 계약. 지금 DB 적재는 v1-abcmart 원본 dict를 Adapter가 직접 변환

공통 규칙

규칙내용
additionalProperties: false스키마에 없는 필드가 하나라도 있으면 그 상품은 검증 실패 — 새 필드를 크롤러에 추가하면 스키마도 같이 고쳐야 한다
price 문자열"19,000원" 형태 고정 (^$|^[0-9,]+원$) — 숫자·통화코드 분리는 운영 계약(v1)의 몫
verification 서브스키마두 site 계약 모두 동일한 status / compared_fields / differences / json_source_url / html_source_url / verified_at 구조 공유

v1-unified 핵심 필드

두 site 결과를 하나의 배열로 다루기 위한 최소 공통 집합. site 전용 리뷰 필드는 없으면 null로 채운다 (ABC마트: detail_scores/review_color/is_best, 29CM: user_size/partner_comment/size_survey/is_blind).

필드타입비고
source_product_id, title, brand, link, sitestring필수
price, price_originalstring필수, "원" 문자열 유지
discount_percent, rating, review_countnumber | null필수(값은 null 허용)
image_url, images[], color, style_codestring필수
category, category_path, in_stockstring / bool|null필수
options.colors[], options.sizes[]string[]29CM sizes는 options[].value에서 정규식으로 KR 사이즈만 추출
reviews[]object[]공통 6필드 + site 전용 필드(null 채움)

6. 실행 예시

scripts/run_unified_crawl.py 구두

두 크롤러를 동시 실행 → site별 contract 검증 → normalize → 하나의 output/unified_*.json으로 저장한 실제 결과에서 상품 1건씩 발췌 (리뷰 배열은 길이만 표시).

abcmart · 이브 웨지 3
{
  "price": "19,000원", "discount_percent": 61,
  "category": "웨지", "in_stock": true,
  "rating": 4.5, "review_count": 13,
  "options": {
    "colors": ["BLACK"],
    "sizes": ["225","230","235","240","245","250"]
  },
  "reviews": "[13개, 전량 수집]"
}
29cm · BELLA SLINGBACK
{
  "price": "119,280원", "discount_percent": 29,
  "category": "플랫", "in_stock": true,
  "rating": 4.5, "review_count": 766,
  "options": {
    "colors": ["BLACK"],
    "sizes": ["230","235","240","245","250"]
  },
  "reviews": "[716개, 전량 수집]"
}
review_count ≠ len(reviews)일 수 있음 — 29CM 리뷰 API가 응답하는 count(766)와 실제로 페이지네이션으로 끝까지 받아지는 results 총량(716)이 다르다. 직접 API를 마지막 페이지까지 호출해 확인한 값이라 우리 쪽 페이지네이션 버그가 아니라 29CM API 자체의 카운트 오차다. review_count는 API가 보고하는 값을 그대로 두고, reviews[]는 실제로 받아올 수 있었던 만큼만 채운다.

키워드 "구두" · 판매처당 5~10개 기준 실행에서 contract 위반 0건, unified-product.schema.json 전량 통과를 확인했다.

7. 남은 논의거리

구조ABC마트 카테고리 크롤링(crawl_category)은 아직 HTML 전용 — 키워드 검색처럼 JSON 우선 + 검증용 브라우저로 리팩토링할지
범위운영 계약 contracts/collector/v1(Go Collector 전제)이 여전히 미구현 — 지금 DB 적재는 v1-abcmart 원본을 Adapter가 직접 변환해 우회 중
범위§3.3 자연어 검색 → 추천 파이프라인(dev-jw)은 이번에 이식하지 않음 — Spring 쪽 API 자체가 달라서 별도 작업 필요
속도리뷰 전량 수집이 기본값이 되면서 리뷰 많은 상품(700+)은 상품당 페이지 요청이 늘어남 — 대량 실행 전 요청 예산/시간 상한 정책 필요
