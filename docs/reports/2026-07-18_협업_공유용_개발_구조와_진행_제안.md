# Purchase Research Agent 협업 공유 자료

작성일: 2026-07-18

## 가장 먼저 알아야 할 것

사용자는 **Next.js로 만든 챗봇 화면만 본다.**

사용자가 챗봇에 질문하면 다음 순서로 처리한다.

```text
사용자
→ Next.js chatbot UI
→ Codex CLI
→ MCP Server
→ Python Backend
→ Go Collector
→ 실제 쇼핑몰
```

결과는 반대 순서로 돌아와 Next.js 챗봇 화면에 표시된다.

## 어떤 서비스를 만들려는가

사용자가 다음과 같이 질문한다고 가정한다.

> 10만 원 이하 270 사이즈 면접용 구두를 찾아줘.

우리 서비스는 다음 작업을 한다.

1. 사용자의 예산, 사이즈, 용도를 이해한다.
2. 실제 쇼핑몰에서 조건에 맞는 상품을 찾는다.
3. 가격, 재고, 옵션과 출처를 정리한다.
4. 여러 상품을 비교해서 보여준다.
5. 구매 직전에 가격과 재고를 다시 확인한다.

## 각 부분은 무슨 일을 하는가

### Next.js

사용자가 보는 서비스다.

- 챗봇 화면을 보여준다.
- 사용자의 질문을 Codex에 전달한다.
- 진행상황과 상품 결과를 보여준다.

Next.js 안에는 사용자가 보는 화면과 질문을 전달하는 기능이 함께 들어간다. 사용자는 이 둘을 구분할 필요가 없다.

### Codex

사용자의 질문을 이해하고 어떤 작업이 필요한지 판단한다.

예를 들어 `270 사이즈 구두를 찾아줘`라는 질문을 받으면 상품 검색 기능을 사용하기로 결정한다.

### Plugin

Codex에게 구매 조사를 어떤 순서로 해야 하는지 알려주는 설명서다.

예를 들면 다음 규칙을 알려준다.

- 필요한 사이즈나 예산이 없으면 먼저 질문한다.
- 상품 검색 기능을 사용한다.
- 출처가 없는 상품 정보는 만들어내지 않는다.
- 구매 전에는 가격과 재고를 다시 확인한다.

### MCP

Codex가 사용할 수 있는 기능 목록이다.

```text
상품 검색
상품 상세 조회
리뷰 조회
상품 비교
가격·재고 재확인
```

Codex는 사용자의 질문에 맞는 MCP 기능을 선택한다.

### Python Research Backend

구매 조사 전체를 정리하는 중심 역할이다.

- Go Collector에 상품 검색을 요청한다.
- 수집된 데이터가 올바른지 검사한다.
- 상품 정보를 같은 형식으로 정리한다.
- PostgreSQL에 저장한다.
- 상품을 비교하고 근거를 연결한다.
- Codex가 사용할 MCP 기능을 제공한다.

### Go Collector

실제 쇼핑몰에 접속해서 공개 상품 정보를 가져온다.

- 상품명
- 브랜드
- 가격
- 상품 주소
- 이미지
- 사이즈
- 재고

Collector는 데이터를 가져오기만 한다. 어떤 상품이 좋은지는 판단하지 않는다.

## 사용자가 질문했을 때 실제 흐름

```text
1. 사용자가 Next.js 챗봇에 질문한다.
2. Next.js가 질문을 Codex에 전달한다.
3. Codex가 질문을 이해한다.
4. Codex가 MCP의 상품 검색 기능을 선택한다.
5. Python Backend가 Go Collector에 검색을 요청한다.
6. Go Collector가 실제 쇼핑몰 정보를 가져온다.
7. 결과가 Codex로 돌아온다.
8. Codex가 이해하기 쉽게 정리한다.
9. Next.js가 사용자에게 답변을 보여준다.
```

직접 확인한 정보:

- 실제 ABC마트 상품 검색
- 상품명과 브랜드
- 가격
- 상품 주소와 이미지
- 공개된 사이즈
- 사이즈별 재고 상태
- 정보 출처와 수집 시각

실제 테스트에서는 `구두`, `270 사이즈`, `재고 있음` 조건으로 상품 3건을 확인했다.

아직 없는 정보:

- 배송비
- 상품 상세 옵션
- 평점과 리뷰 개수
- 리뷰 내용
- 리뷰를 이용한 착화감 분석

## 오늘 작업한 내용

- Go Collector에서 실제 ABC마트 검색 구현 및 확인
- 검색 결과를 JSON으로 반환하는 API 구성
- 요청 사이 최소 1초 간격 적용
- timeout과 응답 크기 제한
- 외부 주소로 잘못 이동하는 요청 차단
- 단위 테스트와 실제 쇼핑몰 테스트 분리
- 테스트 파일을 `tests` 폴더로 이동
- 사용하지 않는 빈 폴더와 파일 제거
- 전체 Go 테스트와 코드 검사 통과

## 쇼핑몰 범위

처음에는 ABC마트와 무신사만 대상으로 한다.

### ABC마트

현재 공개 검색 정보를 가져올 수 있다.

### 무신사

현재 일반 수집기 접근이 robots 정책에 의해 차단되어 있다. 이를 우회하지 않고, 허용된 방법이 확인될 때 구현한다.

## 쇼핑몰 화면이 바뀌면 어떻게 할 것인가

현재 크롤링 구조 상, 쇼핑몰 화면 구조가 바뀌면 수집 코드도 영향을 받을 수 밖에 없는 구조이다.
이를 완전히 자동으로 바로 수정하면 잘못된 가격이나 재고를 보여줄 위험이 있다. 따라서 쇼핑몰 html 구조를 자동화으로 감지하여 크롤러 코드도 자동 수정되는 기능이 필요하다고 예상하고 있다.

```text
쇼핑몰 구조 변경 감지
→ 어떤 정보가 사라졌는지 확인
→ 수정 코드 자동 제안
→ 자동 테스트
→ 사람이 확인
→ 실제 반영
```

즉, 자동으로 문제를 발견하고 수정안을 만들되 최종 반영은 사람이 확인한다.

## 오픈소스로 확장하고 싶은 방향

PoC에서는 먼저 Codex CLI와 Codex Plugin을 사용한다. 하지만 최종 목표는 Codex만 있어야 실행되는 프로젝트가 아니다.

사용자가 자신의 환경에 맞는 AI를 선택할 수 있게 만드는 것이 좋다.

```text
사용자
  ↓
Next.js 화면
  ↓
사용할 AI 선택
  ├── Codex CLI + Codex Plugin
  ├── Claude Code
  ├── Ollama로 실행한 로컬 모델
  ├── llama.cpp로 실행한 로컬 모델
  └── 직접 운영하는 GPU 모델 서버
  ↓
공통 MCP Server
  ↓
Python Research Backend
  ↓
Go Collector
  ↓
실제 쇼핑몰
```

쉽게 말하면 아래 네 부분은 그대로 사용한다.

- Next.js 화면
- MCP Server
- Python Research Backend
- Go Collector

그 앞에서 질문을 이해하고 필요한 기능을 고르는 AI만 바꿀 수 있게 만든다.

이를 위해 Python Backend 앞에 **AI 연결부**를 둔다. AI 연결부는 선택한 AI에게 질문과 사용할 수 있는 기능 목록을 전달하고, AI가 상품 검색 기능을 선택하면 공통 MCP Server를 호출한다.

### 왜 AI 연결부가 필요한가

Ollama나 llama.cpp로 모델을 실행했다고 해서 그 모델이 MCP를 자동으로 사용할 수 있는 것은 아니다.

다음 과정을 대신 처리하는 작은 연결 프로그램이 필요하다.

```text
사용자 질문 전달
→ AI에게 사용 가능한 기능 알려주기
→ AI가 선택한 기능 확인
→ MCP 기능 실제 호출
→ 검색 결과를 다시 AI에게 전달
→ 사용자에게 최종 답변 전달
```

이 연결 프로그램을 프로젝트에서는 `AI Runtime Adapter`라고 부를 수 있다. 문서와 대화에서는 이해하기 쉽게 `AI 연결부`라고 표현한다.

### 개발 단계

#### PoC 단계

- Codex CLI와 Codex Plugin으로 전체 흐름을 먼저 완성한다.
- Claude Code에서도 같은 MCP 기능을 사용할 수 있는지 함께 확인한다.
- 이 단계에서는 상품 검색이 실제로 처음부터 끝까지 동작하는지가 가장 중요하다.

#### PoC 통과 후

- [Ollama](https://github.com/ollama/ollama) 연결부를 추가해 개인 PC에서 로컬 모델로 실행한다.
- [llama.cpp](https://github.com/ggml-org/llama.cpp)의 API Server 연결부를 추가해 더 가벼운 로컬 실행 방법을 제공한다.
- GPU 서버에 올린 모델을 연결해 여러 사용자가 함께 사용하는 환경을 시험한다.
- 같은 질문과 같은 상품 데이터로 AI별 결과를 비교한다.

Ollama는 로컬에서 모델을 실행하고 REST API로 호출할 수 있다. llama.cpp도 로컬과 서버 환경에서 모델을 실행할 수 있고 OpenAI 호환 API Server를 제공한다.

### Codex와 Claude Code 설정을 함께 관리하는 방법

Codex와 Claude Code는 규칙 파일, 명령어 파일, MCP 설정 위치가 서로 다르다. 각 파일을 따로 수정하면 시간이 지나면서 내용이 달라질 수 있다.

따라서 프로젝트 안에 **공통 원본 한 개**를 두고 각 도구가 요구하는 형식으로 만들어주는 방식을 검토한다.

- [Rulesync](https://github.com/dyoshikawa/rulesync): 하나의 원본에서 여러 AI 개발 도구용 규칙, 명령, MCP 설정 등을 생성하거나 변환할 수 있다.
- [AgentSync](https://github.com/dallay/agentsync): `.agents/`를 공통 원본으로 사용하고 Codex, Claude Code 등의 설정 위치에 연결하며 MCP 설정도 함께 관리할 수 있다.

현재 프로젝트는 이미 `AGENTS.md`와 `.agents/`를 사용하고 있으므로 AgentSync 방식이 구조상 이해하기 쉽다. 다만 바로 의존성을 추가하지 않고 두 도구를 작은 예제로 시험한 뒤 하나를 선택한다.

현재 AgentSync 문서를 기준으로 보면 Codex의 규칙, skill, MCP 설정 동기화는 지원하지만 Codex용 custom command 동기화는 지원 목록에 표시되어 있지 않다. 따라서 **Codex와 Claude Code의 명령어 통합이 가장 중요한 목적이라면 Rulesync를 먼저 시험**하고, 공통 명령을 skill로 제공하는 방법도 함께 검토한다.

중요한 점은 Rulesync와 AgentSync가 **개발 규칙과 명령어의 중복 관리를 줄여주는 도구**라는 것이다. 이 도구들만 설치한다고 Ollama나 GPU 모델이 MCP를 자동으로 사용하는 것은 아니다. 로컬 모델과 GPU 모델에는 앞에서 설명한 AI 연결부가 별도로 필요하다.

### AI별 결과를 비교할 때 확인할 것

- 한국어 질문을 제대로 이해하는가?
- 필요한 MCP 기능을 정확하게 선택하는가?
- 가격, 재고, 근거를 임의로 만들지 않는가?
- 정해진 JSON 형식으로 결과를 안정적으로 만드는가?
- 답변 속도와 동시에 처리할 수 있는 사용자 수는 적절한가?
- 필요한 GPU 메모리와 운영 비용은 감당할 수 있는가?
- 모델과 실행 도구의 라이선스가 서비스 목적에 맞는가?

최종 목표는 다음과 같다.

```text
AI를 바꿔도
화면, MCP, Backend, Collector는 다시 만들지 않는다.
```

## REST API Server와 MCP Server의 차이

REST API Server와 MCP Server는 모두 Python Backend의 기능을 외부에서 사용할 수 있게 해준다. 다만 **누가 기능을 선택하고 호출하는지**, 그리고 **기능을 어떤 형태로 제공하는지**가 다르다.

### REST API Server

REST API는 Next.js, 모바일 앱, 다른 백엔드와 같이 일반 프로그램이 정해진 URL을 직접 호출하는 방식이다.

예를 들어 상품 검색 기능이 다음과 같이 제공될 수 있다.

```text
POST /api/products/search
```

요청 데이터는 일반적으로 JSON 형태로 전달한다.

```json
{
  "query": "면접용 구두",
  "size": 270,
  "maxPrice": 100000,
  "inStockOnly": true
}
```

Next.js는 어떤 API를 호출해야 하는지 미리 알고 있어야 한다.

```text
Next.js
→ POST /api/products/search 호출
→ Python Backend
→ Go Collector
→ 검색 결과 반환
```

즉, REST API에서는 개발자가 다음 내용을 직접 구현한다.

- 어떤 URL을 호출할지
- 어떤 HTTP Method를 사용할지
- 어떤 JSON 데이터를 보낼지
- 응답을 어떻게 화면에 표시할지
- 검색 후 상세 조회가 필요하면 어떤 API를 추가 호출할지

REST API는 호출 과정이 명확하고 일반적인 웹 서비스 구조에 적합하다. Next.js 화면에서 상품 검색 버튼을 누르거나, 검색 결과를 저장하는 것처럼 **호출할 기능이 이미 정해져 있는 경우**에 사용하기 좋다.

### MCP Server

MCP Server는 Codex와 같은 AI Agent가 사용할 수 있는 기능을 도구 형태로 제공한다.

예를 들어 Python Backend의 상품 검색 기능을 다음과 같은 MCP Tool로 제공할 수 있다.

```text
search_products
```

이 기능에는 이름뿐만 아니라 설명과 입력 형식도 함께 정의된다.

```json
{
  "name": "search_products",
  "description": "예산, 사이즈, 용도 등의 조건으로 실제 쇼핑몰 상품을 검색한다.",
  "input": {
    "query": "string",
    "size": "number",
    "max_price": "number",
    "in_stock_only": "boolean"
  }
}
```

Codex는 사용자의 자연어 요청을 읽고 어떤 기능을 호출할지 스스로 판단한다.

```text
사용자: 10만 원 이하 270 사이즈 면접용 구두를 찾아줘.

Codex 판단:
- 상품 검색이 필요함
- search_products 도구를 사용해야 함
- query = 면접용 구두
- size = 270
- max_price = 100000
- in_stock_only = true
```

그다음 Codex가 MCP Server에 구조화된 요청을 보낸다.

```text
Codex
→ search_products 호출
→ MCP Server
→ Python Backend
→ Go Collector
→ 검색 결과 반환
```

검색 결과를 받은 뒤 추가 작업이 필요하면 Codex가 다음 도구를 이어서 선택할 수도 있다.

```text
search_products
→ get_product_detail
→ compare_products
→ verify_price_and_stock
```

즉, MCP에서는 Next.js 개발자가 모든 호출 순서를 미리 고정하지 않아도 된다. 사용자의 질문과 현재 대화 내용을 보고 Codex가 필요한 기능과 실행 순서를 판단한다.

### 핵심 차이

REST API는 **프로그램이 정해진 주소를 직접 호출하는 방식**이다.

```text
Next.js
→ POST /api/products/search
```

MCP는 **AI Agent가 사용할 수 있는 기능을 도구로 등록하는 방식**이다.

```text
Codex
→ search_products
```

REST API에서는 Next.js 개발자가 호출 대상을 결정한다.

MCP에서는 Codex가 사용자의 질문을 해석한 뒤 호출할 기능을 결정한다.

### 같은 기능을 두 방식으로 제공할 수 있다

REST API Server와 MCP Server가 서로 완전히 다른 상품 검색 로직을 가지는 것은 아니다.

두 방식 모두 내부적으로는 같은 Python 함수를 사용할 수 있다.

```python
def search_products(query, size, max_price, in_stock_only):
    # Go Collector 호출
    # 결과 검증
    # 데이터 정규화
    # 결과 반환
    pass
```

REST API에서는 이 함수를 HTTP Endpoint와 연결한다.

```text
POST /api/products/search
→ search_products()
```

MCP Server에서는 같은 함수를 MCP Tool과 연결한다.

```text
search_products
→ search_products()
```

전체 구조는 다음과 같다.

```text
                    ┌→ REST API: POST /api/products/search
Python 검색 로직 ───┤
                    └→ MCP Tool: search_products
```

즉, 상품 검색 로직을 중복 구현하는 것이 아니라 **하나의 내부 기능을 REST API와 MCP 두 가지 방식으로 노출하는 구조**다.

### 이 프로젝트에서 REST API가 필요한 경우

REST API는 다음과 같은 기능에 적합하다.

- Next.js에서 로그인 요청
- 이전 대화 내역 조회
- 저장된 상품 목록 조회
- 찜한 상품 저장 및 삭제
- 검색 이력 조회
- 관리자 화면에서 수집 상태 조회
- 사용자가 특정 버튼을 눌렀을 때 정해진 기능 실행

이 기능들은 AI가 어떤 도구를 사용할지 판단할 필요가 없다. Next.js에서 호출할 API가 명확하게 정해져 있기 때문이다.

### 이 프로젝트에서 MCP가 필요한 경우

MCP는 사용자의 자연어 요청에 따라 실행 과정이 달라지는 기능에 적합하다.

예를 들어 사용자가 다음과 같이 요청할 수 있다.

> 10만 원 이하 270 사이즈 구두를 찾아서 착화감이 편한 순서로 비교해줘. 구매 전에 재고도 다시 확인해줘.

Codex는 이 요청을 여러 단계로 나누어 처리해야 한다.

```text
1. 상품 검색
2. 상품 상세 조회
3. 리뷰 조회
4. 착화감 관련 리뷰 분석
5. 상품 비교
6. 가격과 재고 재확인
7. 최종 답변 작성
```

이처럼 사용자 요청마다 필요한 기능과 실행 순서가 달라지는 경우 MCP가 적합하다.

### 이 프로젝트에서의 역할 구분

이 프로젝트에서는 다음과 같이 역할을 나눌 수 있다.

```text
Next.js
- 사용자가 보는 챗봇 화면
- 로그인과 대화 내역 관리
- Codex 실행 요청
- 결과 출력

REST API Server
- Next.js에서 직접 사용하는 일반 백엔드 API
- 사용자, 대화, 검색 이력, 저장 상품 관리
- 필요하면 상품 검색 기능을 직접 호출할 수 있는 HTTP API 제공

MCP Server
- Codex가 사용할 수 있는 구매 조사 도구 제공
- 상품 검색, 상세 조회, 비교, 재고 재확인 기능 등록

Python Backend
- REST API와 MCP가 공통으로 사용하는 실제 비즈니스 로직
- Go Collector 호출
- 데이터 검증과 정규화
- PostgreSQL 저장
- 상품 비교와 근거 연결
```

전체 구조는 다음과 같이 볼 수 있다.

```text
사용자
→ Next.js chatbot UI
→ Codex

Codex
→ MCP Server
→ Python Backend
→ Go Collector
→ 쇼핑몰

Next.js
→ REST API Server
→ Python Backend
→ PostgreSQL
```
