# Python 크롤러 기능 검증과 통합 비교표

작성일: 2026-08-09

## 결론

정우님 Python 구현은 ABC마트/29CM의 검색과 상세/옵션/리뷰 수집 범위가 가장 넓다.
기존 `services/python-collector`는 대량 수집 안전장치와 재현 가능한 실행 환경이 가장
잘 갖춰져 있다. 최신 Go 구현은 현재 Spring Boot가 사용하는 RabbitMQ 계약과 운영 실패
처리가 가장 완성되어 있다.

따라서 Python 전환 방향은 정우님 구현을 기능 골격으로 사용하고, 기존 Python 구현의
대량 수집 안전장치와 최신 Go 구현의 Queue 계약/실패 처리를 Python으로 옮기는 방식이
적절하다. 지금 세 구현을 파일 단위로 바로 합치거나 Go Collector를 제거하면 안 된다.

정우님과 우선 합의할 내용은 다음 세 가지다.

1. 최종 Python runtime 위치를 `purchase-research-agent`로 정할지 결정한다.
2. 별도 `crawl_jobs` Queue를 폐기하고 현재 Spring Boot CollectionTask/CollectionResult
   계약을 Python Worker가 그대로 사용할지 결정한다.
3. 상세/옵션/리뷰 기능을 유지하면서 요청 예산/checkpoint/429 즉시 중단 같은 안전장치를
   어느 순서로 이식할지 결정한다.

## 확인된 핵심 문제

### P0 통합 전에 반드시 해결

1. `purchase-research-agent/scripts/rabbitmq_crawl.py`는 `crawl_jobs`라는 독립 Queue와 자체
   payload를 사용한다. Spring Boot와 최신 Go가 사용하는
   `purchase-research.collection.search.v1`/`purchase-research.collection.result.v1`
   계약과 연결되지 않는다.
2. Worker가 크롤링 예외를 `errors` 배열로 바꾼 뒤 `message.process()`를 정상 종료하므로
   실패 작업도 ACK된다. retry Queue/DLQ/result publisher confirm이 없다.
3. ABC마트 상세 API Client가 `verify=False`로 TLS 인증서 검증을 끈다. 운영 전 반드시
   기본 인증서 검증으로 되돌리고 실패 원인을 확인해야 한다.
4. 상세/옵션/리뷰/RabbitMQ/FastAPI 저장 API를 직접 검증하는 자동 테스트가 없다.
5. dependency lock과 Python version 불일치는 Python 3.12.11/`uv.lock` 전환으로
   해결했다. 이후 설치와 테스트는 `uv sync --frozen`/`uv run --frozen`만 사용한다.

### P1 운영 안정성을 위해 이식

1. 기존 Python 비교기의 요청 예산/wall time/checkpoint/resume/중복 통계/429 즉시 중단을
   정우님 runtime에 이식한다.
2. process별 Semaphore만으로는 전체 요청량을 통제하지 못하므로 판매처별 전역 rate limit을
   Redis adapter 또는 단일 작업 조정 계층과 연결한다.
3. 옵션은 단순 문자열 목록을 넘어 색상/사이즈 조합별 재고와 sourceUrl/collectedAt/
   collectorVersion을 보존하는지 contract test로 확인한다.
4. 리뷰 작성자 식별정보는 최종 Adapter에서 제외되고 있지만 사진 존재 여부와 공개 출처
   참조는 현재 CollectorResult에 전달되지 않는다. 저장할 신호 범위를 합의한다.
5. CORS `allow_origins=["*"]`와 `allow_credentials=True` 조합을 실제 호출 주체에 맞게 제한한다.

### P2 이후 확장

1. 무신사 또는 신발 외 판매처 추가 우선순위를 정한다.
2. 실제 판매처 smoke test를 opt-in으로 만들고 CI 기본 실행에서는 제외한다.
3. 같은 fixture/같은 Contract/같은 요청 정책으로 Python 전환 전후 처리량과 오류율을 다시
   측정한다.

## 제안하는 작업 순서

1. [완료] Python 3.12/`uv.lock`으로 환경을 고정하고 현재 13개 테스트를 재현한다.
2. 최신 Go의 CollectionTask/CollectionResult v1 fixture를 Python contract test로 먼저 옮긴다.
3. Python Worker를 현재 search/result Queue에 연결하고 ACK/retry/DLQ/publisher confirm을
   통합 테스트한다.
4. `verify=False`를 제거하고 401/403/429/timeout/5xx 정책을 테스트한다.
5. 상세/옵션/리뷰 fixture를 보강하고 개인정보/출처/수집 시각 계약을 확인한다.
6. 요청 예산/checkpoint/resume과 판매처별 전역 rate limit을 이식한다.
7. 3건/10건/100건 순으로 opt-in 실수집하고 마지막에 기존 10,000개 기준을 다시 측정한다.
8. Python E2E가 통과한 뒤에만 Go runtime 제거와 브랜치 병합 범위를 결정한다.

## 구현 후 갱신

같은 날 `purchase-research-agent`에 현재 CollectionTask/CollectionResult v1을 사용하는
Python Worker를 추가했다. page 1부터 200 전달, 가격/카테고리/사이즈/색상/재고 필터,
prefetch 1, persistent 발행, publisher confirm 뒤 ACK, retry attempt 증가와 작업 DLQ를
구현했다. 24개 Python 단위 테스트와 격리된 로컬 RabbitMQ vhost의 success/retry/DLQ
통합 검증이 통과했다. 따라서 위 비교표의 Spring Queue 연결과 retry/DLQ 항목은 구현
시점 이전의 차이를 설명하는 기록으로 읽는다.

후속 `MERCHANT-001` 작업에서 Python HTTP client와 Crawl4AI의 TLS 인증서 검증을
활성화하고 자동 redirect를 제거했다. 401/403은 접근 통제로 즉시 중단하고 429/5xx만
재시도 가능한 일시 오류로 분류한다. 경고에는 URL/query, 응답 body와 traceback을
포함하지 않으며 정적 검사로 위험한 설정 재도입을 차단한다.
