# Python/Go 크롤러 확장성과 성능 비교 보고서

작성일: 2026-08-04

## 1. 한눈에 보는 결론

이번 PoC에서 Python과 Go 모두 ABC마트/29CM 공개 검색 상품을 페이지 단위로 수집하고,
상품 ID 중복 제거/checkpoint 재개/gzip NDJSON 저장/공통 Contract 검증까지 수행했다.

- ABC마트: 두 언어 모두 고유 상품 9,417개 수집
- 29CM: 두 언어 모두 고유 상품 10,000개 수집
- Contract: 네 조합의 최대 단계 결과 38,834개 전체 통과
- 오류/429: 모든 단계에서 0회
- 실제 수집 속도: 요청 간 1초 제한 때문에 Python과 Go가 거의 같음
- 저장 fixture parser: Go가 Python보다 약 7.25배에서 8.88배 높은 처리량
- 최대 메모리: 최대 단계에서 Go 약 22MB/Python 약 53MB 이하

따라서 현재 조건에서는 Go가 parser 처리량과 메모리 면에서 유리하다. 다만 실제
판매처 수집 시간은 네트워크와 1초 요청 간격이 대부분이므로, Go를 쓰면 실수집이 무조건
몇 배 빨라진다고 해석하면 안 된다.

## 2. 무엇을 같은 조건으로 비교했나

### 공통 조건

- 판매처: ABC마트/29CM
- 검색어 순서: 구두/운동화/스니커즈/러닝화/샌들/슬리퍼/부츠/신발/여성화/남성화
- 페이지당 최대 50개
- 판매처 요청 간 최소 1초
- timeout 15초
- 일시 오류 재시도 최대 1회
- 고유 상품 최대 10,000개
- 401/403/429 즉시 중단
- 상품 ID 기준 중복 제거
- `contracts/collector/unified`의 `v1-unified` 검증

로그인/CAPTCHA/접근 제한을 우회하지 않았고 공개 검색 화면이 사용하는 응답만 낮은
빈도로 순차 요청했다. Python과 Go 실수집을 동시에 실행하지 않았다.

### 비교를 두 종류로 나눈 이유

1. 실제 수집 E2E: HTTP 요청부터 정규화/Contract 검증/압축 저장까지 측정한다.
2. 저장 fixture parser: 네트워크 없이 같은 JSON bytes를 반복 decode하고 정규화한다.

실제 수집 E2E에는 판매처 응답 시간과 의도적인 1초 대기가 들어간다. 언어 처리 성능은
저장 fixture 결과를 함께 봐야 한다.

## 6. 데이터 완전성 차이

Contract 통과는 필수 형식이 맞다는 뜻이며 두 언어가 모든 선택 필드를 똑같이 채웠다는
뜻은 아니다.

- Python ABC마트 Adapter는 원가/할인율/style code를 원본 JSON에서 비교 계약으로 옮긴다.
- Go는 운영 `CollectorResult.Product`에 있는 사실만 비교 Adapter로 옮긴다.
- 현재 Go 운영 모델에 없는 원가/할인율/style code는 빈 문자열 또는 null로 남는다.
- 29CM도 Python이 원가/할인율을 더 많이 보존해 누락 필드 수가 적다.

그래서 최대 단계 누락 필드는 Python이 더 적다. 이는 Python 언어가 더 정확해서가 아니라
두 운영 모델이 보존하는 필드 범위가 다르기 때문이다. 다음 개발에서 Go 운영 계약에
원가/할인율이 필요한지 팀이 결정하고, 필요하면 Spring 저장 계약까지 함께 확장해야 한다.

## 7. 현재 확장 구조에서 확인한 것

- 판매처별 HTTP/JSON 해석은 Adapter에 분리됐다.
- 대량 반복/중복 제거/checkpoint/요청 예산/압축 저장은 공통 Runner가 담당한다.
- 새 판매처는 Adapter와 공통 Contract 변환을 추가하면 Runner를 재사용할 수 있다.
- 대량 결과는 `tmp/`에 두고 Git에 커밋하지 않는다.
- 현재 최대 단계 명령은 한 process에서 순차 실행하며 RabbitMQ 분산 수집은 아니다.
- 운영 확장 시 RabbitMQ는 페이지 작업/결과 전달, Redis는 전역 rate limit/중복 방지/
  짧은 상태에만 사용한다.

바로 Worker 수를 늘리면 판매처 요청량도 같이 늘 수 있다. 따라서 분산 Worker를 만들기
전에 Redis 기반 판매처 전체 1초 제한을 먼저 구현해야 한다.

## 8. 권장 선택

운영 Collector 기본 구현은 Go를 유지하는 편이 합리적이다.

1. 저장 fixture parser에서 CPU와 메모리 효율이 좋았다.
2. 현재 RabbitMQ Worker와 운영 `CollectorResult`가 이미 Go에 연결돼 있다.
3. 많은 페이지 작업을 처리할 때 제한된 goroutine과 작은 메모리 사용을 활용하기 쉽다.

Python 구현은 버리지 않고 비교/reference Adapter와 새 판매처 구조 탐색에 활용할 수
있다. Python으로 빠르게 판매처 JSON 구조를 검증한 뒤 같은 Contract 테스트를 통과하는
Go Adapter로 옮기는 방식도 가능하다.

## 9. 재현 명령

### Go

```bash
cd services/collector
go test ./...
go test -race ./...
go vet ./...

go run ./cmd/parser-benchmark -merchant abcmart -iterations 1000 -warmup 100
go run ./cmd/parser-benchmark -merchant 29cm -iterations 1000 -warmup 100
```

대량 수집은 `go run ./cmd/batch`에 `-query`를 반복하고 `-max-items`,
`-request-budget`, `-min-interval`, `-output-dir`를 명시한다.

### Python

Python 코드는 `sandbox-python-croller/ls` 브랜치에 있다.

```bash
cd services/python-collector
uv sync
uv run python -m unittest discover -s tests -v

uv run python -m purchase_collector.benchmark --merchant abcmart --iterations 1000 --warmup 100
uv run python -m purchase_collector.benchmark --merchant 29cm --iterations 1000 --warmup 100
```
