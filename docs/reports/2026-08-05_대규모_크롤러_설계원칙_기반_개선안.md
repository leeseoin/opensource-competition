# 대규모 크롤러 설계 원칙 기반 개선안

작성일: 2026-08-05
참고 자료: https://jaeseo0519.tistory.com/489 (시스템 설계 관점의 대규모 웹 크롤러 설계 정리 — 분산 처리, 정중함(politeness), 우선순위, 장애 복구 등)

## 목적

참고 글은 "월 10억 페이지" 규모의 범용 웹 크롤러(검색엔진용) 설계를 다루기 때문에 이 저장소의
`purchase-research-agent` 크롤러(ABC마트/29CM 2개 판매처, 키워드당 수백~수천 개)에 그대로 적용할
내용은 아니다. 다만 원칙 단위로 보면 지금 코드에 이미 반영된 것과, 스케일이 커질 때 문제가 될
지점을 짚어주는 것들이 섞여 있어 항목별로 대조했다.

## 원칙별 대조

### 1. 호스트별 큐 / 정중함(Politeness) — 부분 반영, 스케일 시 구멍 있음

**원칙**: 같은 호스트에는 동시에 한 요청만 보내고, 호스트별로 별도 큐에서 처리해 특정 사이트에
부하가 몰리지 않게 한다.

**현재 상태**:
- 검색 페이지네이션은 사이트별로 페이지 간 1초 sleep으로 순차 처리 중
  (`app/crawlers/abcmart/crawler.py:140`, `app/crawlers/cm29/crawler.py:97`).
- 29CM 상세 수집은 이번에 `asyncio.Semaphore(10)`로 동시 요청 수를 제한하도록 바꿈
  (`app/crawlers/cm29/detail_fetcher.py`).
- **구멍**: 이 제한은 전부 "한 번의 크롤링 실행" 안에서만 유효하다. `CrawlerService.search_items()`
  (`app/services/crawler_service.py:15`)는 호출될 때마다 새 크롤러 인스턴스 + 새 HTTP client를
  만들기 때문에, 사용자가 같은 사이트를 동시에 여러 번 검색하면 (예: API로 동시 요청 2~3개) 사이트
  기준 실질 요청 속도는 그만큼 배가 된다. 지금은 요청량이 적어 문제가 안 됐을 뿐, 서비스로 커지면
  가장 먼저 터질 지점이다.

**개선 제안**:
- 사이트(호스트)별로 프로세스 전역 `asyncio.Semaphore`를 하나씩 두고, `crawl()`/`attach_details()`
  안의 개별 요청이 이 전역 세마포어를 통과하도록 바꾼다. 지금처럼 크롤러 인스턴스마다 새로 만들지
  않고 모듈 레벨 싱글턴으로 공유해야 동시 요청 여러 건이 들어와도 사이트 기준 상한이 유지된다.
- 이미 RabbitMQ 기반 수집 작업 큐가 붙어 있으니 (커밋 `d29ee62`, `17498d5`), 장기적으로는
  "호스트별 워커/큐"를 애플리케이션 세마포어가 아니라 큐 소비자 수 자체로 제한하는 방식이 더
  참고 글의 구조에 가깝다.

### 2. 타임아웃 — 이미 반영

`timeout=10~15`가 모든 `httpx.AsyncClient` 생성부에 이미 지정돼 있다. 추가 조치 불필요.

### 3. DNS 캐싱 / 커넥션 재사용 — 부분 반영

**원칙**: DNS 조회(10~200ms)가 매 요청마다 반복되면 병목이 되므로 캐싱하거나 커넥션을 재사용한다.

**현재 상태**: 검색 단계는 `async with httpx.AsyncClient(...)` 블록 안에서 client를 재사용해 커넥션
풀/keep-alive 이득을 이미 보고 있다. 다만 명시적인 `httpx.Limits(max_connections=..., max_keepalive_connections=...)`
설정이 없어 기본값(전체 100, keepalive 20)에 의존 중이다. 세마포어 동시성(10~20)과 커넥션 풀 상한이
안 맞으면 keep-alive가 예상보다 자주 끊겨 재협상 비용이 생길 수 있다.

**개선 제안**: `httpx.AsyncClient(limits=httpx.Limits(max_keepalive_connections=concurrency, max_connections=concurrency))`
처럼 세마포어 동시성 값과 커넥션 풀 상한을 맞춰준다. 별도 DNS 캐시 레이어는 사이트가 2개뿐인
현재 규모에서는 과함 — 필요 없음.

### 4. robots.txt 준수 — 수동 확인만 되어 있음

**현재 상태**: 이번 대화에서 29CM/ABC마트 `robots.txt`를 수동으로 확인해 크롤링 대상 경로가 막혀
있지 않음을 확인했다. 코드에는 이를 강제하는 부분이 없다.

**개선 제안**: 이 프로젝트 규모에서는 자동 검사기를 만들기보다, 사이트 추가 시 체크리스트 항목으로
"robots.txt + 이용약관 크롤링 조항 확인"을 문서화해두는 것으로 충분하다 (원칙 자체도 "robots.txt는
법적 구속력이 제한적인 경고문"이라고 언급함 — 실제 리스크 판단은 이용약관 쪽이 더 중요하다는 점은
이전 대화에서 다룬 것과 일치).

### 5. 중복 제거 — 이미 반영, 신선도(재크롤링) 관점은 미반영

**현재 상태**: 상품 ID 기준 dedup은 이미 있다 (`seen_prdt_nos`/`seen_ids`, ABC마트·29CM 각각).

**미반영 부분**: 참고 글의 "우선순위/신선도" 개념 — 이미 수집한 상품을 재수집할 때 변경 여부를
판단해 우선순위를 매기는 로직은 없다. 지금 구조는 매 실행마다 검색 결과 전체를 처음부터 다시
훑는다.

**개선 제안 (가격 추적 기능을 만들 계획이라면 유효)**: 상품별로 마지막 수집 시각 + 가격/재고
스냅샷을 저장해두고, 재수집 시 "가격/할인율이 바뀐 상품" 또는 "일정 기간 재수집 안 된 상품"부터
우선 처리하는 큐를 두면 참고 글의 Prioritizer 개념과 맞아떨어진다. 지금 당장 필요한 기능은
아니라 우선순위는 낮게 잡는다.

### 6. 장애 복구 / 영속 저장 — 사이트마다 다름 (핵심 구멍)

**현재 상태**:
- `services/python-collector`: gzip NDJSON + `checkpoint.json`으로 중단 후 `--resume` 재개 가능
  (`services/python-collector/src/purchase_collector/runner.py`).
- `purchase-research-agent/scripts/run_unified_crawl.py`: **중간 저장이 전혀 없다.** 두 사이트
  크롤링 + 상세 수집이 전부 끝난 뒤에야 `output/unified_*.json` 파일 하나로 저장한다
  (`run_unified_crawl.py:57-64`).

**리스크**: 이전 대화에서 짚었듯, 대량 수집(예: 10,000개) 도중 차단/네트워크 오류로 중단되면
그때까지 모은 결과가 전부 날아간다. 참고 글의 "크롤링 상태와 데이터를 persistent storage에 기록해
장애 시 재시작" 원칙이 이 경로에는 적용돼 있지 않다.

**개선 제안 (우선순위 최상위)**: `run_unified_crawl.py`에 `python-collector`가 이미 쓰는 것과 같은
패턴 — 페이지/상품 단위로 결과를 즉시 append 저장 + checkpoint 파일 갱신 — 을 이식한다. 이미 검증된
패턴이 저장소 안에 있으니 새로 설계할 필요 없이 포팅만 하면 된다.

### 7. 예외 격리 — 파일마다 다름 (두 번째로 중요한 구멍)

**현재 상태**:
- `app/services/crawler_service.py:56-66` `search_multi_site()`는 `asyncio.gather(..., return_exceptions=True)`로
  이미 사이트 간 예외를 격리하고 있다 (주석에도 명시).
- `scripts/run_unified_crawl.py:44-46`의 `asyncio.gather(*(_crawl_site(...) ...))`는
  **`return_exceptions=True`가 없다.** 한 사이트에서 처리 안 된 예외가 나면 다른 사이트가 진행 중이던
  작업까지 취소되고 전체 스크립트가 실패한다.

**개선 제안**: `run_unified_crawl.py`도 `crawler_service.py`와 같은 패턴으로 `return_exceptions=True`를
추가하고, 예외를 사이트별 errors 리스트에 담아 나머지 사이트 결과는 살리도록 맞춘다. 이건 한 줄
수준의 수정이라 비용 대비 효과가 크다.

### 8. 데이터 검증 — 이미 반영

`app/services/contract_validation.py`가 JSON Schema로 상품 단위 검증 후 위반 상품을 제외하는 구조라
참고 글의 "데이터 검증 필수" 원칙과 이미 일치한다. 추가 조치 불필요.

### 9. 분산 처리(consistent hashing 등) — 현재 규모에서는 불필요

참고 글의 핵심인 다중 서버 분산/일관성 해싱은 판매처 2곳, 키워드 단위 실행인 지금 규모에는
과한 설계다. RabbitMQ 기반 작업 큐가 이미 있으니, 나중에 여러 워커로 확장할 때 "호스트별 큐 라우팅"
개념만 필요한 시점에 가져오면 된다 — 지금 미리 만들 필요는 없음.

## 우선순위 정리

| 순위 | 항목 | 이유 | 비용 |
|---|---|---|---|
| 1 | `run_unified_crawl.py`에 `return_exceptions=True` 추가 | 원칙 #7, 한 사이트 실패가 전체를 죽이는 걸 막음 | 매우 낮음 (한 줄) |
| 2 | `run_unified_crawl.py`에 checkpoint/resume 이식 | 원칙 #6, 대량 수집 시 진행 상황 유실 방지 — 10,000개 스케일 논의에서 나온 리스크 | 중간 (python-collector 패턴 포팅) |
| 3 | 사이트별 전역 세마포어로 정중함 상한 공유 | 원칙 #1, 동시 요청 여러 건 들어올 때 사이트 기준 속도 상한 유지 | 중간 |
| 4 | httpx `Limits`를 concurrency와 맞춤 | 원칙 #3, 커넥션 재사용 효율 | 낮음 |
| 5 | 가격/신선도 기반 재수집 우선순위 | 원칙 #5, 가격 추적 기능이 실제로 필요해질 때 | 높음 (기능 설계 필요) |

1, 2, 4는 지금 바로 적용해도 부작용이 적은 항목이라 원하시면 이어서 구현하겠습니다.
