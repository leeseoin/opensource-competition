# AI 쇼핑 추천 에이전트 시스템 설계 및 요구사항 (AI Shopping Assistant System Design)

## 1. 시스템 개요 (System Overview)
사용자가 "면접용 구두를 사고 싶어"라고 요청했을 때, 크롤링을 통해 상품 정보를 수집하고 정제하여 AI가 최종적으로 사용자에게 적합한 상품을 추천해 주는 시스템입니다. 
본 문서는 크롤링 수행 주체 및 흐름에 따른 두 가지 분기(Branch)를 분석하고, 최종 추천 알고리즘을 구현하기 위한 요구사항과 개발 스펙을 정의합니다.

## 2. 시나리오 분석 및 아키텍처 분기 (Scenario & Architecture Branches)

### 2.1. 사용자 요청 흐름
- **입력**: "면접용 구두를 사고 싶어"
- **기본 처리 흐름**: 자연어 이해(NLU) ➔ 검색 키워드 추출("면접용 구두") ➔ 데이터 수집(크롤링) ➔ 데이터 정제 ➔ AI 분석 및 추천 ➔ 결과 반환

---

### 분기 1: AI 서버가 주도하는 크롤링 (Function Calling 방식)
이 방식은 AI가 스스로 판단하여 어떤 데이터를 수집할지 결정하고, 외부에 마련된 도구(Tool)를 호출하는 **에이전트(Agentic)** 구조입니다.

- **실행 흐름**:
  1. **요청 전달**: 클라이언트 ➔ 백엔드 ➔ AI 파이썬 서버로 사용자 요청 전달.
  2. **AI의 판단 (Function Calling)**: AI(LLM)가 요청을 분석하여 상품 정보가 필요함을 인지하고, `web_scraper(query: "면접용 구두")` 형태의 도구 실행 명령(JSON)을 백엔드에 내림.
  3. **크롤링 실행**: 백엔드(또는 별도의 워커 서버)가 명령을 받아 크롤링 라이브러리를 통해 타겟 사이트 검색 및 HTML 데이터 수집.
  4. **데이터 정제**: 수집된 방대한 HTML에서 상품명, 가격, 리뷰 등 핵심 텍스트만 추출(DOM 파싱, 불필요 태그 제거).
  5. **AI에 데이터 전달 및 추천**: 정제된 데이터를 다시 AI 서버에 주입, AI가 이를 바탕으로 사용자 추천 텍스트를 생성하여 백엔드로 반환.
- **장점**: 
  - **확장성**: 추후 쇼핑 외에 날씨, 환율, 뉴스 등 다양한 도구(Tool)를 쉽게 추가하고 AI가 알아서 선택하게 할 수 있음.
  - **유연성**: 검색어가 모호할 경우 AI가 알아서 검색 키워드를 구체화하여 도구를 여러 번 호출 가능.
- **단점**: 
  - LLM API를 여러 번 왕복해야 하므로 레이턴시(응답 지연)가 길어질 수 있음.
  - 시스템 설계 및 상태(State) 관리가 다소 복잡함.

---

### 분기 2: 백엔드가 주도하는 크롤링 및 파이프라인 (Direct Crawling 방식)
이 방식은 백엔드 시스템이 크롤링과 정제를 먼저 끝내고, AI에게는 '추천(분석)' 역할만 맡기는 **파이프라인(Pipeline)** 구조입니다.

- **실행 흐름**:
  1. **요청 분석 및 크롤링**: 클라이언트의 "면접용 구두" 요청을 백엔드가 직접 받아, 즉시 쇼핑몰 검색 URL로 크롤링을 수행.
  2. **데이터 정제**: 백엔드 내부의 파싱 라이브러리(Jsoup, BeautifulSoup 등)를 사용해 HTML 데이터를 파싱하고 핵심 상품 데이터만 정제.
  3. **AI 추천 요청**: 사용자 원래 요청("면접용 구두 사고 싶어")과 **정제된 크롤링 데이터(JSON/Text)**를 한 번에 AI 파이썬 서버로 전달.
  4. **최종 응답**: AI는 전달받은 데이터를 바탕으로 추천 답변을 생성하여 백엔드에 반환.
- **장점**: 
  - 시스템 구조가 단순하고 직관적.
  - LLM 호출이 단 1회(또는 최소화)로 끝나므로 응답 속도가 빠르고 비용이 절감됨.
- **단점**: 
  - AI의 자율성이 제한됨. 사용자 요청이 쇼핑이 아닐 경우(예: "면접 잘 보는 법 알려줘")에도 무조건 크롤링을 시도하거나, 별도의 룰베이스(분기 처리 로직)를 백엔드에 꼼꼼히 짜두어야 함.

## 3. 추천 알고리즘 및 AI 분석 구현 (Recommendation Logic)

크롤링을 통해 수집한 데이터를 바탕으로 사용자에게 최적의 구두를 추천하는 과정입니다. 

- **필요한 입력 데이터 (AI Context)**: 
  - 정제된 상품 목록 (예: `[{상품명: A, 가격: 150000, 디자인특징: "스트레이트 팁", 평점: 4.5, 주요리뷰: "면접용으로 깔끔해요"}, ...]`)
  - 사용자 정보 및 컨텍스트 ("면접용", 단정한 디자인, 신뢰감)
- **AI의 분석 프롬프트 로직**:
  1. **조건 매칭**: 면접용(포멀한 디자인, 튀지 않는 색상 등)에 부합하는 상품인지 데이터 내의 특징을 통해 필터링.
  2. **비교 및 선별**: 가성비, 리뷰 긍정 비율을 종합적으로 고려하여 Top 2~3개 상품을 선별.
  3. **추천 사유(Reasoning) 작성**: 사용자에게 "이 상품은 광택이 과하지 않고 단정(스트레이트 팁)하며, 후기에서도 착화감이 좋아 면접용으로 추천합니다" 와 같이 개인화된 근거를 함께 제시.

## 4. 시스템 요구사항 및 개발 스펙 (Specs & Requirements)

### 4.1. 기술 스택 (Tech Stack)
- **Backend (Main Server)**: 
  - Node.js (NestJS) 또는 Java (Spring Boot)
  - 역할: 클라이언트 API 제공, 워크플로우 제어, 분기 2의 경우 크롤링 직접 수행.
- **AI/Crawling Server**: 
  - Python (FastAPI), LangChain 또는 LlamaIndex
  - 역할: LLM 연동, Function Calling 처리(분기 1), 파이썬 기반 크롤러 실행.
- **크롤링 및 정제 (Crawling & Parsing)**:
  - **정적 페이지**: BeautifulSoup4, lxml, Jsoup
  - **동적 렌더링(SPA) 페이지**: Selenium, Puppeteer, Playwright
  - **정제 로직**: `Trafilatura`, `Readability.js` 또는 자체 DOM 트리 파싱 로직 (광고, nav, footer 제거)
- **LLM 모델**: GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Pro 등 (컨텍스트 윈도우가 크고 Function Calling 기능이 우수한 모델 필수)

### 4.2. 주요 기능 모듈
1. **의도 분석기 (Intent Analyzer)**: 사용자의 질문이 크롤링이 필요한 요청인지 파악 (분기 2를 채택할 경우 백엔드에 필수적으로 필요).
2. **크롤링 에이전트/서비스**: 특정 URL 또는 검색어 쿼리를 받아 쇼핑몰 리스트 페이지와 상세 페이지의 HTML을 가져오는 모듈. 프록시/User-Agent 로테이션 등 크롤링 차단 우회 기법 필요.
3. **데이터 정제기 (Data Cleanser)**: 수집된 원본 HTML에서 불필요한 태그를 버리고, `JSON` 형태의 핵심 상품 객체로 변환하여 토큰 낭비를 막는 모듈.
4. **추천 생성 프롬프트 엔진**: 정제된 데이터를 AI 모델에 주입할 때 사용할 프롬프트 템플릿 엔진.

### 4.3. 시스템 고려 및 제약사항 (Considerations)
- **토큰 최적화 (Token Optimization)**: 상품 10개의 HTML을 그대로 넣으면 수십만 토큰이 발생하여 비용이 폭발합니다. 크롤링 직후 반드시 JSON이나 Markdown 형태의 요약 데이터로 변환해야 합니다.
- **지연 시간 (Latency) 관리**: 실시간 크롤링은 네트워크 지연이 큽니다. 클라이언트(사용자 UI) 쪽에서는 로딩 스피너나 "상품을 검색 중입니다...", "리뷰를 분석 중입니다..." 등 진행 상황을 SSE(Server-Sent Events) 또는 WebSocket을 통해 단계별로 보여주어 사용자 경험(UX)을 개선해야 합니다.
- **법적 문제**: 대형 쇼핑몰의 무단 크롤링은 차단당할 수 있습니다. 1차적으로는 쇼핑몰에서 제공하는 공식 Open API(예: 네이버 쇼핑 API 등) 사용을 우선하고, 크롤링은 보조 수단으로 설계하는 것이 좋습니다.
