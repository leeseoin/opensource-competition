# 기능 목록 동기화

아키텍처 문서를 기능의 원본으로 사용해 기능 목록을 갱신한다. 구현 상태를 코드로
감사하거나 코드 변경 기록을 만드는 작업은 수행하지 않는다.

## 입력 문서

다음 순서로 읽는다.

1. `docs/architecture/*.md`
2. `AGENTS.md`와 `docs/development/기능_ID_기반_개발_추적_프로세스.md`
3. `docs/planning/Purchase_Research_Agent_기능_목록.md`
4. `docs/planning/Purchase_Research_Agent_TODO.md`

기능 목록이 없으면 새로 만든다. 기존 기능 ID와 기능 정의는 삭제하거나 재번호를
부여하지 않는다.

## 기능 추출 절차

1. 아키텍처에서 사용자가 이용하거나 시스템이 제공해야 하는 독립 기능을 찾는다.
2. 구현 단계나 파일 작업이 아니라 검증 가능한 결과 단위로 기능을 나눈다.
3. 같은 기능이 여러 문서에 나오면 하나로 합치고 모든 설계 근거를 연결한다.
4. 기존 기능과 의미가 같으면 기존 ID를 사용한다.
5. 새 기능이면 영역 prefix의 마지막 번호 다음 ID를 부여한다.
6. 기능명, 범위, 완료 기준, 우선순위, 설계 근거를 작성한다.
7. 새 기능의 상태는 `계획`으로 시작한다. 기존 상태는 `feature-progress`의 감사 없이
   올리지 않는다.
8. 아키텍처에서 제거된 기존 기능은 삭제하지 않고 `보류` 후보로 표시한 뒤 이유를
   남긴다.

## ID 규칙

다음 prefix를 기본으로 사용한다.

- `CONTRACT`: 서비스 사이의 요청과 응답 계약
- `COLLECTOR`: 판매처 데이터 수집
- `MERCHANT`: 판매처 추가와 접근 안전성
- `QUEUE`: RabbitMQ 작업 흐름
- `REDIS`: 속도 제한, 중복 방지, 짧은 상태
- `BACKEND`: Spring Boot와 PostgreSQL
- `MCP`: MCP Server와 AI 실행 연결
- `WEB`: Next.js 사용자와 관리자 화면
- `ANALYSIS`: 리뷰 신호와 상품 비교
- `VERIFY`: 구매 전 재검증
- `OPS`: 로컬 실행, CI, 문서와 운영
- `RUNTIME`: Codex, Claude Code, 로컬 LLM과 GPU 실행 환경

형식은 `<PREFIX>-<3자리 번호>`를 사용한다. 예시는 `BACKEND-001`이다.

## 기능 목록 필수 열

- 기능 ID
- 기능명
- 영역을 나타내는 표 열 또는 구역 제목
- 상태
- 우선순위
- 범위
- 완료 기준
- 설계 근거
- 다음 작업

상태는 기능 목록 문서에 정의된 값만 사용한다.

## 금지 사항

- 실제 코드와 테스트를 확인하지 않고 상태를 완료로 변경하지 않는다.
- TODO의 세부 작업마다 새로운 기능 ID를 만들지 않는다.
- 번호가 비었다는 이유로 기존 ID를 재정렬하지 않는다.
- 아키텍처에 근거가 없는 기능을 추측해 추가하지 않는다.
- 코드, commit, push를 변경하지 않는다.

## 완료 확인

- 기능 ID가 중복되지 않는지 확인한다.
- 각 기능에 하나 이상의 설계 근거가 있는지 확인한다.
- 완료 기준이 테스트 가능한 문장인지 확인한다.
- 날짜를 `YYYY-MM-DD` 형식으로 갱신한다.
- 변경한 기능 ID와 변경 이유를 사용자에게 요약한다.
