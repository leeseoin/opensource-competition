# 코드 변경 기록 작성

기능 목록에 등록된 하나의 기능 ID를 기준으로 완료된 구현이나 버그 수정의 사실을
기록한다. 기능의 최종 완료 상태는 판정하지 않고 실제 변경과 검증만 남긴다.

## 입력 확인

1. 사용자가 지정한 기능 ID를
   `docs/planning/Purchase_Research_Agent_기능_목록.md`에서 확인한다.
2. 기능 ID가 없거나 여러 기능이 섞이면 추측하지 말고 기록 범위를 먼저 나눈다.
3. `git status --short`, `git log --oneline -10`과 관련 `git show <hash>`를 확인한다.
4. 기능 구현 commit이 없으면 코드트래커 완료 기록을 만들지 않고 commit이
   필요하다고 안내한다.
5. 관련 TODO, 개발 진행 관리, source와 test를 확인한다.

## 기록 절차

1. commit에서 실제 변경된 파일과 기능 ID의 관련성을 확인한다.
2. 핵심 class/function/method/schema와 시작 줄을 찾는다.
3. 문제 수정이면 증상, 확인된 원인과 해결 방법을 구분한다.
4. 현재 작업에서 실제 실행한 검증만 기록한다.
5. 검증하지 않은 동작은 `미검증`으로 표시한다.
6. `docs/reports/코드트래커/<YYYY-MM-DD>-<기능-ID>-<주제>.md`를 작성한다.
7. `docs/reports/코드트래커/INDEX.md`의 최신 기록 목록 맨 위에 추가한다.
8. 같은 날짜와 기능 ID 기록이 이미 있으면 중복 파일 대신 기존 기록을 보완한다.

## 기록 형식

```md
# YYYY-MM-DD <기능-ID> <주제>

- 기능 ID: `<기능-ID>`
- 구현 commit: `<hash>`
- 기록 상태: 구현 기록/버그 수정 기록

## 배경과 범위

왜 변경했고 어디까지 구현했는지 적는다.

## 구현 내용

- `path/to/file:줄` `SymbolName`: 책임과 변경 내용

## 발생 문제와 원인

확인된 사실만 적는다. 문제가 없으면 `없음`으로 적는다.

## 해결

적용한 변경과 선택 이유를 적는다.

## 검증

- `검증 명령`: 통과/실패와 핵심 결과

## 남은 작업

남은 범위가 없으면 `없음`으로 적는다.
```

INDEX 형식은 다음을 사용한다.

```md
- YYYY-MM-DD / [`<기능-ID>` <제목>](<파일명>.md) / `<commit>` / 핵심 한 줄
```

## 작성 원칙

- 사실 기반으로 간결하게 작성한다.
- 기존 기록과 INDEX 항목을 삭제하지 않는다.
- 코드 전체를 붙이지 않고 파일 경로, 시작 줄과 심볼을 기록한다.
- 기능 목록이나 TODO의 완료 상태를 직접 변경하지 않는다.
- commit, push와 PR은 사용자가 별도로 요청할 때만 수행한다.
- 한국어 문서에 가운데점 문장 부호를 사용하지 않는다.
