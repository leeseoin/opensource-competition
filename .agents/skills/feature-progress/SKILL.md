# 기능 진행상황 점검

문서 주장만 믿지 않고 실제 코드와 검증 근거를 확인해 기능별 현재 상태를 판정한다.
선택한 기능 ID만 점검하는 것을 기본으로 하고, 사용자가 요청하면 전체 기능을
점검한다.

## 입력

다음 자료를 모두 확인한다.

1. `docs/planning/Purchase_Research_Agent_기능_목록.md`
2. 기능의 설계 근거로 연결된 `docs/architecture/*.md`
3. `docs/planning/Purchase_Research_Agent_TODO.md`
4. `docs/reports/코드트래커/INDEX.md`와 관련 기록
5. `docs/development/Purchase_Research_Agent_개발_진행_관리.md`
6. 실제 source, contract, migration, 설정과 test
7. 현재 작업에서 실행한 검증 결과

기능 ID가 없으면 추측하지 말고 `feature-catalog`로 먼저 등록하도록 안내한다.

## 점검 절차

1. 기능 ID의 범위와 완료 기준을 읽는다.
2. 관련 TODO를 정상 경로, 실패 경로, 테스트, 문서와 검증으로 나눈다.
3. 실제 구현 파일과 핵심 class/function/method/schema를 찾는다.
4. 관련 테스트가 존재하는지와 무엇을 검증하는지 확인한다.
5. 안전하게 실행 가능한 검증 명령을 실행한다.
6. 코드트래커의 commit과 현재 코드가 일치하는지 확인한다.
7. 아래 판정 기준으로 상태를 결정한다.
8. 기능 목록의 상태, 다음 작업과 개발 진행 관리의 근거를 함께 갱신한다.

## 상태 판정

- `계획`: 설계와 기능 목록만 있고 구현 코드가 없다.
- `진행 중`: 현재 변경이 시작됐지만 독립적으로 동작하는 정상 경로가 없다.
- `부분 구현`: 정상 경로 일부가 동작하지만 필수 범위, 실패 처리, 테스트 또는 문서가
  남아 있다.
- `구현 완료/검증 필요`: 범위의 코드는 갖춰졌지만 필요한 테스트, 실제 통합 검증,
  계약 검증 또는 문서가 남아 있다.
- `완료`: 완료 기준 전체와 정상 경로, 실패 경로, 테스트, 문서 및 검증 명령이
  확인됐다.
- `차단`: 외부 정책, 권한, 합의 또는 환경 변화가 없으면 진행할 수 없다.
- `보류`: 팀 결정으로 현재 개발 대상에서 제외됐다.

## 문서 갱신 규칙

- 기능 목록에는 상태, 다음 작업과 최종 점검일을 갱신한다.
- 개발 진행 관리에는 기능 ID, 상태, 구현 파일의 시작 줄, 심볼, 테스트와 검증
  명령을 기록한다.
- TODO는 원자 작업이 실제로 완료된 경우에만 `[x]`로 변경한다.
- 일부만 끝난 작업은 `[ ]`을 유지하고 `**(진행 중)**` 또는 부분 구현 설명을 붙인다.
- 줄 번호만 기록하지 않고 항상 파일 경로와 심볼을 함께 기록한다.
- 과거 기록을 삭제하거나 현재 판단에 맞게 소급 수정하지 않는다.

## 완료 판정 금지 조건

다음 중 하나라도 해당하면 `완료`로 판정하지 않는다.

- 코드트래커만 있고 실제 코드가 없다.
- 테스트 파일은 있지만 해당 기능을 검증하지 않는다.
- 검증 명령을 실행하지 않았거나 실패했다.
- 계약, migration 또는 문서 갱신이 완료 기준에 포함되지만 빠져 있다.
- 실제 판매처 smoke test가 필요한 기능인데 opt-in 검증을 하지 않았다.
- 남은 실패 경로가 사용자 데이터 손실이나 잘못된 근거 생성으로 이어질 수 있다.

## 최종 보고

기능 ID별로 상태, 충족한 완료 기준, 남은 기준, 코드 근거, 실행한 검증과 다음 작업을
간결하게 보고한다. commit과 push는 사용자가 별도로 요청할 때만 수행한다.
